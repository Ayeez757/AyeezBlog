# AyeezBlog 压测经验笔记

本文档从已执行的 JMeter 公网压测中提炼**可复用经验**，与正式阈值、长文分析区分：偏实操、偏教训、偏检查项。详细数据与章节论述见文末关联文档。

---

## 1. 环境与结论边界（先写清楚再开跑）

| 项 | 经验 |
| --- | --- |
| **服务器规格** | 当前基线为 **2C4G、公网峰值约 5 Mbps**；换机器或带宽后，旧结论不可直接对比。 |
| **压测发起位置** | **本地 PC → 公网域名（HTTPS）** 测的是端到端体验，长尾里常有本地出网、TLS、链路抖动；**不能与「同地域 ECS → 目标」的系统容量结论混写在一个 SLA 里。** |
| **入口** | 公网场景以 **`https://域名/api`** 为准；脚本里用 **`base_path=/api`** 与 **`__P()` 传参** 保持与线上一致。 |
| **生产安全** | 只读线程组、**关闭 track / 管理端 / 写场景** 再压生产；否则 PV、登录、写库会污染数据与结论。 |

---

## 2. 工具链与命令习惯

| 项 | 经验 |
| --- | --- |
| **`-J` 与 PowerShell** | 参数可能被错误拆分；**整条命令用引号包参数**，或 **`cmd /c "jmeter ..."`**，避免 `-Jhost=...` 失效。 |
| **JMeter 用户属性** | TestPlan / HTTP 默认值里用 **`${__P(name,default)}`**，保证命令行 **`-Jthreads=20`** 等真正覆盖脚本中的并发、协议、主机、端口、`base_path`。 |
| **HTML 报告** | 每次 **`-e -o` 的输出目录必须为空**；否则生成失败或混入上一轮数据。 |
| **归档** | 大体积 `.jtl`、整包 `reports/` 可按仓库策略 **不提交**，但要在文档里写清**结论表与命令**，便于复现。 |

---

## 3. 时长：粗测与精测不要混用结论

| 项 | 经验 |
| --- | --- |
| **粗测** | `hold_sec` 取 **180～300s** 适合快速扫区间，结论务必标注 **「粗测」**。 |
| **精测** | 定档、写报告用 **`hold_sec` 600～900s**，与 `AyeezBlog-性能指标标准.md` 一致。 |
| **教训** | 曾出现 **短时粗测认为 20/40 线程「像 S 档」**，但 **900s 精测** 下全接口分位与 Total 长尾仍不达标。**正式结论以长稳态为准。** |

---

## 4. 看报告时看哪里

| 项 | 经验 |
| --- | --- |
| **全局** | Dashboard **Statistics → Total**：错误率、`pct2`/`pct3`（约 P95/P99）、吞吐。 |
| **分接口** | 每个 G1 label（如 `Public /post/list`）单独看 P95/P99；**S 档要求「每个 G1 都达标」，只看 Total 会漏判。** |
| **原始字段** | `statistics.json` 里 **Total** 与各 transaction 与 HTML 表一致，便于存档对比。 |

---

## 5. 指标分层：别用一条线量所有事

| 项 | 经验 |
| --- | --- |
| **G1-S** | 全局错误率 ≤0.1%，且 **每个 G1 P95≤200ms、P99≤800ms**；极严，适合「对内宣传或合同级」前先在同地域压测验证。 |
| **G1-A** | 更贴近本报告历史 SLA（如错误率 &lt;0.5%、P95 &lt;300ms 量级）；**公网博客类对外承诺可优先对齐 A**。 |
| **本地→公网实测** | 在 **5～63 线程、900s 精测** 下，**未找到同时满足 G1-S 的档位**；即使 **5 线程、0% 错误**，Total P95 仍在 **600ms+**。说明 **延迟线不是「再降并发」就能单独解决**，链路侧比重大。 |

---

## 6. 高并发（threads=80）只读基线带来的教训

| 观测 | 经验 |
| --- | --- |
| **错误率约 2.36%** | 不满足宽松 SLA，更不满足 G1 分级中的 A/B 上层目标。 |
| **错误形态** | 以 **`Connect timed out`** 为主，**读超时**为辅；**各接口都有**，更像 **连接/网关/链路容量** 而非某一 SQL。 |
| **P99 贴 5s、Max 极大** | 典型 **长尾 + 超时边界**；排查时优先 **并发连接、Nginx upstream、带宽与超时配置**，再查应用与 DB。 |

---

## 7. 阶梯压测怎么排期更省时间

| 项 | 经验 |
| --- | --- |
| **冒烟** | L0：**5～10 线程**，确认脚本、域名、TLS、断言无误。 |
| **找拐点** | 再按 **20 → 40 → 60 → 80** 加压，每阶独立 JTL + HTML。 |
| **定 S 档上限** | 标准文档推荐 **同地域 ECS** 做 G1-S；若坚持本地→公网，应预期 **可能得不到「S 档最大并发」数字**，只能得到 **体验型结论**。 |

---

## 8. 优化与复测时的优先级（与报告一致）

1. **P0**：网关与网络（连接数、`keepalive`、超时、安全组、TCP 队列、**5 Mbps 是否打满**）。
2. **P0**：应用线程池与连接超时（避免线程与连接堆积放大长尾）。
3. **P1**：MySQL 慢查询与索引、热点读缓存。
4. **P2**：管理端、写场景 **单独成组** 压测，避免与公网只读混在一起读不懂瓶颈。

---

## 9. 一轮压测结束后的自检清单

- [ ] 是否写明：**协议、域名、端口、`/api`、threads、ramp、hold、是否只读**？
- [ ] 结论来自 **粗测还是精测**？
- [ ] 判档是否覆盖 **Total + 每个 G1 接口**？
- [ ] 压测端是 **本机还是云上**，是否与对外承诺口径一致？
- [ ] 大文件是否已忽略提交，但 **结论表或截图** 已进文档？
