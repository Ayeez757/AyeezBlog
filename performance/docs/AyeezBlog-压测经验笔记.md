# AyeezBlog 压测经验笔记（本地 Docker 环境）

本文档从你当前的“本地 Docker 固定资源环境 + JMeter 脚本”压测中提炼**可复用经验**，偏实操、偏教训、偏检查项；旧的公网压测结论与旧表格不再在本文出现。

---

## 1. 环境与结论边界（先写清楚再开跑）

| 项 | 经验 |
| --- | --- |
| **固定资源** | 后端容器固定为 **`cpus=2.0`、`mem_limit=4g`**（并建议 JVM `-Xms3g -Xmx3g`）。换资源就必须重新定标。 |
| **入口** | 本地压测入口是 **`http://localhost:8080`** 且**无 `/api` 前缀**，脚本参数用 `-Jbase_path=""`。 |
| **数据库** | MySQL 与后端同 `docker-compose.perf-local.yml` 编排，后端用 `HM_DB_HOST=mysql` 直连服务名；主机的 3306 端口冲突时不要映射 MySQL 端口。 |
| **零污染** | 只读压测保持 **`write_threads=0`**，并确保管理端/写场景线程组保持关闭。 |

---

## 2. 工具链与命令习惯

| 项 | 经验 |
| --- | --- |
| **`-J` 与 PowerShell** | 参数可能被错误拆分；**整条命令用引号包参数**，或 **`cmd /c "jmeter ..."`**，避免 `-Jhost=...` 失效。 |
| **JMeter 用户属性** | TestPlan / HTTP 默认值里用 **`${__P(name,default)}`**，保证命令行 **`-Jthreads=20`** 等真正覆盖脚本中的并发、协议、主机、端口、`base_path`。 |
| **HTML 报告** | 每次 **`-e -o` 的输出目录必须为空**；否则生成失败或混入上一轮数据。 |
| **归档** | 大体积 `.jtl`、整包 `reports/` 可按仓库策略 **不提交**，但要在文档里写清**结论表与命令**，便于复现。 |
| **Spring AI 启动** | 若本地压测不使用 AI 功能，也要提供 `SPRING_AI_OPENAI_API_KEY`（可用占位值）避免应用启动失败。 |

---

## 3. 时长：粗测与精测不要混用结论

| 项 | 经验 |
| --- | --- |
| **粗测** | `hold_sec` 取 **180～300s** 适合快速扫区间，结论务必标注 **「粗测」**。 |
| **精测** | 定档、写报告用 **`hold_sec` 600～900s**，与 `AyeezBlog-性能指标标准.md` 一致。 |
| **教训** | **必须区分“服务端瓶颈”与“压测端瓶颈”**：本地单机压测在高并发下可能先触发压测端临时端口耗尽（见第 6 节）。 |

---

## 4. 看报告时看哪里

| 项 | 经验 |
| --- | --- |
| **全局** | Dashboard **Statistics → Total**：错误率、`pct2`/`pct3`（约 P95/P99）、吞吐。 |
| **分接口** | 每个 G1 label（如 `Public /post/list`）单独看 P95/P99；**S 档要求「每个 G1 都达标」，只看 Total 会漏判。** |
| **原始字段** | `statistics.json` 里 **Total** 与各 transaction 与 HTML 表一致，便于存档对比。 |

---

## 5. 指标分层：别用一条线量所有事

| 项 | 经验 |
| --- | --- |
| **G1-S** | 全局错误率 ≤0.1%，且 **每个 G1 P95≤200ms、P99≤800ms**；极严，适合「对内宣传或合同级」前先在同地域压测验证。 |
| **G1-A** | 更贴近本报告历史 SLA（如错误率 &lt;0.5%、P95 &lt;300ms 量级）；**公网博客类对外承诺可优先对齐 A**。 |
| **本地压测的目标** | 更适合做 **版本回归、参数对比、找拐点**；若要“宣称容量上限”，需要解决压测端限制或用分布式压测。 |

---

## 6. 两种典型失败形态（压测端 vs 服务端）

| 形态 | 典型现象 | 经验 |
| --- | --- | --- |
| **压测端 `BindException`** | `.jtl` 中 `responseCode` 为 `Non HTTP response code: java.net.BindException` | 不要将该档当作服务端容量上限；先 **Keep-Alive / 扩大临时端口 / 分布式压测**。 |
| **服务端延迟超 S（无 HTTP 错误）** | 错误率 0%，但 **P95/P99 超过 S 阈值**（可能体现在 Total 或单接口） | 以**每接口口径**判档；例如 `279` Total P95=133.95ms 但 `Public /post/list` P95=204ms，严格 S 仍应判不通过。 |

---

## 7. 阶梯压测怎么排期更省时间

| 项 | 经验 |
| --- | --- |
| **冒烟** | L0：**5～10 线程**，确认脚本、域名、TLS、断言无误。 |
| **找拐点** | 再按 **20 → 40 → 80 → 160** 粗测定位区间，然后用 **二分法**（如 120/100/140）收敛到 S 上限。 |
| **定 S 档上限** | 本地单机如遇到 `BindException`，要么先解决压测端瓶颈，要么改用分布式压测，否则“上限”会被压测端限制卡住。 |

---

## 7.1 常见误区（专业报告里应避免）

1. **只看错误率不看分位**：`errorPct=0` 不代表体验达标，S/A/B 判档仍要看 P95/P99。
2. **只看 Total 不看接口**：Total 通过时，单个热点接口可能已超阈值。
3. **把线程数当真实用户数**：线程数是并发会话规模，不是业务 DAU/MAU。
4. **把短时冲高当稳态能力**：Spike 结果不能替代 `hold=900s` 的容量结论。
5. **忽略结论边界**：每次报告都要写清环境、脚本版本、think time、时长和是否只读。

---

## 8. 优化与复测时的优先级（与报告一致）

1. **P0**：压测端与网络栈（是否出现 `BindException`、是否频繁建连、Keep-Alive 是否生效、TIME_WAIT 是否堆积）。
2. **P0**：应用线程池与连接超时（避免线程与连接堆积放大长尾）。
3. **P1**：MySQL 慢查询与索引、热点读缓存。
4. **P2**：管理端、写场景 **单独成组** 压测，避免与只读容量混在一起读不懂瓶颈。

## 9. 一轮压测结束后的自检清单

- [ ] 是否写明：**协议、host、port、base_path、threads、ramp、hold、是否只读**？
- [ ] 结论来自 **粗测还是精测**？
- [ ] 判档是否覆盖 **Total + 每个 G1 接口**？
- [ ] 压测端是 **本机还是云上**，是否与对外承诺口径一致？
- [ ] 大文件是否已忽略提交，但 **结论表或截图** 已进文档？
 
> 注：本地压测默认无 `/api` 前缀；请记录 `base_path` 的实际值（通常为 `""`）。
