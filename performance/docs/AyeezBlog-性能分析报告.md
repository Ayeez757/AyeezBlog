# AyeezBlog 性能分析报告（本地 Docker 固定环境 + JMeter）

## 执行摘要（给决策者）

- 在本地固定环境（后端 `2C4G`）与当前只读模型下，系统在 **严格 S（每接口）**口径下的可承载并发已收敛到 **278**。
- 说明：`279` 在 Total 维度仍满足 S，但接口维度出现 `Public /post/list` P95=204ms（>200ms），因此按严格 S 判为不通过。
- 结论性质：该结论为**稳态承载能力**（`hold_sec=900`），不代表瞬时突发峰值。
- 建议对外保守宣称：**约 250 并发活跃用户**（S 级体验口径）。

## 1. 报告目标

在**固定本地环境**下，对 AyeezBlog 的 **G1 只读接口**做压力/阶梯压测，目标是：

- 给出当前版本在 **S 级指标**下的可达并发区间
- 明确“失败来自服务端，还是来自压测端（JMeter/操作系统网络栈）”
- 形成可复现的命令与结果归档口径（旧结果不沿用）

## 3. 测试环境（固定口径）

### 3.1 被测服务（本地 Docker）

- 后端：`docker-compose.perf-local.yml` 的 `backend` 服务
  - 资源：`cpus=2.0`、`mem_limit=4g`
  - 建议 JVM：`-Xms3g -Xmx3g`
- MySQL：同 compose 编排（`HM_DB_HOST=mysql`）

### 3.2 压测端

- 压测机：本机 Windows + JMeter
- 风险：高并发时可能先触发 **压测端临时端口/TIME_WAIT 限制**（表现为 `java.net.BindException: Address already in use`）

---

## 4. 场景与指标口径

### 4.1 场景（只读）

仅开启只读线程组（TG01），覆盖：

- `GET /post/list`
- `GET /post/get`
- `GET /about/anime/list`
- `GET /links/list`
- `GET /album/list`

并保持：

- `-Jwrite_threads=0`
- 管理端/写场景线程组关闭

### 4.2 S 级判定（摘自标准）

- 全局错误率 ≤ 0.1%
- **每个 G1 接口**：P95 ≤ 200ms 且 P99 ≤ 800ms

### 4.3 负载模型说明（避免误解）

- 当前模型为“固定 5 个只读接口循环 + think time”的**稳态访问模型**，更接近内容浏览型站点。
- 因存在 `think_time`，线程数并不等于“每人连续狂点”；结论应表达为“并发活跃用户能力”。
- 若要评估写入、管理端、突刺流量，需要单独线程组与独立结论。

## 5. 执行命令（可复现）

每档输出独立的 `.jtl` 与 HTML 报告目录（目录必须为空或不存在）。

> 脚本约束：`performance/jmeter/ayeezblog-performance-test.jmx` 已在 `HTTP Request Defaults` 中显式设置 `HTTPSampler.implementation=HttpClient4`，用于强化连接复用（Keep-Alive）并降低压测端临时端口耗尽的概率。

```powershell
jmeter -n -t "performance/jmeter/ayeezblog-performance-test.jmx" `
  -Jprotocol=http -Jhost=localhost -Jport=8080 -Jbase_path="" `

  -Jwrite_threads=0 `
  -Jthreads=80 `
  -l "performance/jmeter/results/max-probe-threads80-900s.jtl" `
  -e -o "performance/jmeter/reports/max-probe-threads80-900s"
```

## 7. 下一步（继续找 S 上限）

### 7.1 S 档结论已收敛后的下一阶段方案

#### 方案 A（推荐）：做“可用性极限/稳定性”测试（非 S）

目标：找到系统在可接受错误率下的最大吞吐与失败形态（超时/拒绝连接/5xx），用于容量规划与保护策略。

- 建议档位：`400 → 600 → 800 → 1000`（每档先粗测 `hold=180~300s`，锁定风险区间后再精测）
- 关注点：错误码分布（5xx/timeout/refused）、P99/Max、CPU/内存/GC、DB 连接等待

#### 方案 B：做“浸泡（Soak）”验证

目标：验证在接近上限但仍稳定的并发下是否存在资源泄漏、连接耗尽、周期性抖动。

- 建议档位：`threads=260~270`
- 建议时长：`hold=3600s`（1 小时）起步

#### 方案 C：做“混合负载”更贴近真实业务

目标：将管理端/写入线程组按比例加入，得到更贴近真实使用的容量结论。

- 方式：在 TG01 基础上逐步开启管理端/写场景（小权重），并单独出报告

### 7.2 建议你下一步跑什么？

由于严格 S 已确定为 `278`，建议你下一步选一个方向：

- 若要验证“稳定性”：跑 **`threads=270，hold=3600s`**
- 若要找“极限能力”：先粗测 **`threads=600，hold=180s`**（观察失败形态与资源，再决定上探还是回退）
判定规则：

- **S 级**：全局错误率 ≤0.1%，且 **Total 与各 G1 接口**的 P95≤200ms、P99≤800ms（以 Dashboard 为准）；
- 若出现 **BindException**，先处理压测端再继续。

## 9. 极限能力测试（非 S，失败形态与保护策略）

### 9.1 测试目的

本章不再追求 S 级阈值，而是回答：

- 系统在高并发下的**主要失败形态**是什么（拒绝连接/超时/业务错误/压测端异常）？
- 失败发生时系统是否能**快速恢复**？
- 是否需要入口限流、连接保护、线程池/连接池调参？

### 9.2 `threads=1000` 实测结果（hold=900s）

数据来源：`performance/jmeter/reports/max-probe-threads1000-900s/statistics.json`

- Total：`sampleCount=260826`，`errorCount=89048`，`errorPct=34.14077%`
- Total：P95≈`2778.95ms`，P99≈`3298.99ms`
- Total：throughput≈`867.99 req/s`

失败类型（按 `.jtl` 失败码聚合）：

- `Non HTTP response code: org.apache.http.conn.HttpHostConnectException`：`89048`（100%）
- `Non HTTP response message: ... Connection refused: getsockopt`：`89048`（100%）

**解释**：该失败形态表示“**服务端端口拒绝新连接**”（连接未建立），通常与服务端连接上限/accept 队列/backlog 饱和或服务进程重启有关。它不同于压测端 `BindException`（客户端无法创建新连接）。

数据来源：对应档位的 `performance/jmeter/reports/max-probe-threads{N}-900s/statistics.json`，失败码来自 `.jtl` 聚合。

| threads | errorPct | Total P95 | Total P99 | Throughput (req/s) | 主失败形态 |
| ---: | ---: | ---: | ---: | ---: | --- |
| 400 | 0.0158% | 616ms | 688ms | 654.40 | `HttpHostConnectException`（connection refused） |
| 600 | 11.1795% | 1487.95ms | 2042ms | 672.37 | `HttpHostConnectException`（connection refused） |
| 800 | 25.8372% | 2267.95ms | 2864.94ms | 753.84 | `HttpHostConnectException`（connection refused） |
| 1000 | 34.1408% | 2778.95ms | 3298.99ms | 867.99 | `HttpHostConnectException`（connection refused） |

补充说明：

- 400/600/800 三档失败码聚合结果均为 **100% `Non HTTP response code: org.apache.http.conn.HttpHostConnectException`**。
- 该失败形态与“请求处理慢导致超时”不同：它发生在**连接建立阶段**，说明服务端在高连接压力下**接不住新连接**（或端口短暂不可用）。

### 9.2.2 结论（极限能力的当前瓶颈）

1. **拐点出现很早**：在 `threads=400` 已出现少量 connection refused，并且 P95/P99 已显著升高。
2. **随并发增长错误率快速上升**：`600 → 800 → 1000` 的错误率呈明显上升趋势，主因仍是拒绝连接。
3. **下一步的主战场**不是业务代码，而是“接入层/连接层”：Web 容器连接上限、accept 队列/backlog、以及是否存在服务进程重启或资源打满导致端口不可用。

### 9.3 建议的后续极限测试方案（更专业的定位方式）

为避免一次性 1000 线程难以定位拐点，建议用“阶梯定位 + 证据采集”的方式：

1. **阶梯粗测（快速定位拐点）**：`400 → 600 → 800 → 1000`，每档 `hold=180~300s`，`ramp_up` 保持较长（如 180s），避免瞬时建连风暴。
2. **拐点精测（复现）**：对首次出现明显 `Connection refused` 的档位与其上一档，各跑 `hold=900s`，确认可复现性。
3. **同步采集证据（必须）**：
   - `docker stats`（CPU/内存是否顶满）
   - 后端容器日志（是否 OOM/重启/报错）
   - 如有条件：服务端端口连接数与 TIME_WAIT（用于判断 backlog/连接上限）
4. **治理与复测**：
   - 若拒绝连接为主：优先调优 Web 容器连接/队列参数（如 Tomcat `max-connections`/`accept-count`/`threads.max`），并加入口限流保护。
   - 若超时为主：优先排查 DB 连接池等待、慢 SQL 与缓存策略。

### 9.4 下一步测试计划（基于已完成 400/600/800/1000）

为了把“拒绝连接”定位到可优化项，建议下一步按两条线并行：

#### 9.4.1 证据采集线（必须补齐）

在跑 `600/800`（任意一档）时，同步记录：

- `docker stats`（backend 容器 CPU/内存是否顶满，是否触发 OOM）
- 后端日志（是否出现重启、端口解绑、异常退出）
- 若可：服务端连接数/队列（用于判断 backlog/连接上限）

#### 9.4.2 复测线（最小成本验证）

1. **先复跑 `threads=600`，hold=180~300s**（粗测复现拒绝连接比例）。
2. 若仍大量 refused：先做 Web 容器连接/队列参数调优（或入口限流），再重复同档粗测对比。
3. 调优有效后，再跑 `threads=800` 粗测验证拐点是否右移。
4. 最终再回到 `threads=1000` 做“调优后极限对比”。

### 9.5 `threads=270` 长稳态（hold=7200s）异常：疑似 OOM / 进程不可用

数据来源：压测端控制台汇总日志 `terminals/2.txt`（命令行参数见文件头部）。

压测参数摘要：

- `threads=270`
- `ramp_up_sec=360`
- `hold_sec=7200`（2 小时）
- `think_time_ms=200`
- 目标：`http://localhost:8080`

#### 9.5.1 现象（从 JMeter 汇总可直接读出的证据）

1. **长时间稳定**：异常发生前，Total 吞吐长期维持在约 `~620 req/s`，Avg 约 `~59~62ms`，错误率 `0%`，属于典型“稳态平台期”。
2. **突发拐点**（约在压测进行到 `01:39:07` 左右）：
   - 单个 33 秒窗口内吞吐骤降到 `77.3/s`
   - Avg 飙升到 `1587ms`
   - Max 出现 `15027ms`
   - 错误率在该窗口内达到 `10.50%`
3. **随后进入“15s 超时风暴”**：紧接的多个 31 秒窗口呈现：
   - 吞吐仅 `~17.6~17.7/s`
   - Avg `~15000ms`，Min `15000ms`，Max `15060ms`
   - 错误率 `100%`
   
   该特征高度符合“**客户端等待到固定超时阈值后失败**”（例如请求/读超时设置为 15s）。
4. **后续出现“快速失败”特征**：再之后的多个 30 秒窗口表现为：
   - 吞吐回到 `~740 req/s` 量级
   - Avg `~11~12ms`，Min `0ms`，Max `~20~30ms`
   - 但错误率仍为 `100%`
   
   该特征更接近“**连接阶段快速失败**”（例如服务端进程不可用导致连接立即失败），而不是业务处理变慢。
5. **本轮最终汇总**：全程 Total 约 `~619.5 req/s`，但累计错误率达到 `17.53%`（`Err=782121`）。

#### 9.5.2 解释（为什么说“疑似 OOM / 进程不可用”）

仅凭 JMeter 汇总无法 100% 断言是 OOM，但本轮呈现的“**平台期稳定 → 突发大量固定 15s 超时 → 随后连接期快速失败**”非常符合以下链路之一：

- **链路 A（更常见）**：内存持续增长 → Full GC/Stop-The-World 时间拉长 → 请求堆积 → 触发客户端 15s 超时 → 最终 OOM 导致进程退出/容器重启 → 连接期快速失败
- **链路 B**：容器内存触顶被 OOM Killer 杀死 → 服务端短时间不可用/重启 → 连接快速失败（若期间仍有部分请求进入等待，也会出现固定超时）

#### 9.5.3 需要补齐的服务端证据（本章结论的“验尸报告”）

要把“疑似”变成“确定”，需要在复现窗口同步采集并归档：

- 后端容器日志：是否出现 `OutOfMemoryError`、应用异常退出、容器重启（启动 banner 重新打印）
- `docker stats`：异常前内存是否持续爬升并顶到 `mem_limit=4g`
- JVM GC 日志（建议开启）：是否在拐点前出现频繁 Full GC/极长停顿
- 若使用连接池/线程池：异常窗口是否出现线程池耗尽、连接池等待爆炸（日志或监控）

#### 9.5.4 下一步怎么测（最低成本复现 + 定位）

- 先用同参数复跑，但把 `hold_sec` 缩短为 `1800s`（30 分钟）观察是否仍在 ~1h+ 位置复现；若复现时间点随时长变化，偏向“泄漏/累积型”问题。
- 保持并发不变（270），只增加证据采集（容器日志、`docker stats`、GC 日志）；**不要一边调参一边复现**，否则证据不可比。
