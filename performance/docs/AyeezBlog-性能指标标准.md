# AyeezBlog 性能指标标准（本地压测环境版）

本文档定义 AyeezBlog 在**本地压测环境**下的性能指标、分级阈值与验收口径，便于版本对比、回归门禁与容量规划。

---

## 1. 适用范围与前提

| 维度 | 说明 |
| --- | --- |
| 环境 | 本文档面向 **本地 Docker 压测环境**。如需公网/生产 SLA，请另立文档与独立定标，不混写。 |
| 协议与入口 | 本地压测以 **HTTP + `localhost:8080` + 无 `/api` 前缀** 为准（脚本传参 `-Jbase_path=""`）。 |
| 负载模型 | 与 `performance/jmeter/ayeezblog-performance-test.jmx` 保持一致时需注明：只读（TG01）、是否含管理端、是否含写入。本文默认只读（TG01）。 |
| 时长 | **基线** ≥ 10 分钟；**容量/回归** ≥ 15 分钟；**浸泡** ≥ 60 分钟（可选）。 |
| 数据 | 本地压测默认 **只读**；写入/埋点需单独定标，避免与只读容量结论混淆。 |

### 1.1 被测环境规格（当前压测基线）

以下规格为**本地压测环境的资源约束**，写入报告与标准时需一并注明，避免不同资源下结论不可比。

| 项目 | 规格 |
| --- | --- |
| 后端容器 CPU | `cpus=2.0` |
| 后端容器内存 | `mem_limit=4g`（并建议 JVM `-Xms3g -Xmx3g`） |
| 数据库 | Docker MySQL（同 compose 网络；库初始化脚本：`AyeezBlog建表.sql`） |

> 说明：本地压测的瓶颈常出现在 **本机资源（CPU/内存/磁盘）**、**数据库** 与 **压测机网络栈（临时端口/TIME_WAIT）**。若出现 `BindException: Address already in use`，优先判定为压测机侧限制，而非服务端极限。

### 1.2 压测发起位置（与结论强绑定）

同一套分级阈值，**压测客户端所在主机不同，结论不可混用**：

| 发起位置 | 典型用途 | 对 G1-S 的含义 |
| --- | --- | --- |
| **同机压测（本机 JMeter → localhost）** | 快速回归、容量摸底 | 易受压测机网络栈影响；出现 `BindException` 时，**该并发档不应作为服务端容量上限**。 |
| **分布式压测（多压测机 → 目标）** | 逼近服务端极限 | 更接近服务端真实上限；用于给出更可信的 **S 档最大并发**。 |

### 1.3 术语约定（报告统一口径）

为避免“线程数、并发用户、RPS”混用导致误读，本项目统一如下：

- **并发用户（Concurrent Users）**：JMeter 线程组中的 `threads`（虚拟用户数），表示同一时段内处于活跃会话的用户规模。
- **请求频率（Req/User/s）**：`Total Throughput / threads`，受 `think_time_ms`、接口链路长度与响应时间共同影响。
- **可承载并发（Capacity under SLO）**：在既定时长与负载模型下，满足 S/A/B 阈值的**最高并发档位**（不是瞬时峰值）。
- **瞬时峰值（Spike）**：短时冲击能力，不等价于稳态承载能力；应与容量结论分章展示。

## 2. 指标分类与统一定义

### 2.1 吞吐（Throughput）

- **RPS**：每秒完成的采样请求数（与 JMeter Dashboard 中 Throughput 一致）。
- **业务吞吐**：可按接口维度统计，用于识别热点接口。

### 2.2 时延（Latency）

- **Avg**：算术平均响应时间（易受长尾拉高，仅作辅助）。
- **P50 / P90 / P95 / P99**：按单次请求耗时升序取分位数；**对外承诺以 P95 为主，稳定性以 P99 与 Max 为辅**。
- 口径：从 JMeter 发起至收到完整响应（含 TLS、网关、应用、数据库）；与 `elapsed` 字段一致。

### 2.3 成功率与错误率

- **成功**：HTTP 2xx 且业务体满足约定（如 JSON 中 `code=200`），与脚本断言一致。
- **错误率** = 失败样本数 / 总样本数 × 100%。  
- **HTTP 非 2xx**、**连接/读超时**、**断言失败** 均计入错误率。

### 2.4 可用性与稳定性（可选但推荐）

- **连续错误窗口**：在滑动 1 分钟内错误率持续 > 1% 视为不稳定，用于浸泡测试。
- **雪崩**：错误率在 5 分钟内从 &lt;0.5% 升至 &gt;5% 且无恢复，记为不合格。

### 2.5 资源与饱和度（与压测报告配套）

在服务器侧同步采集（至少压测窗口内）：

- 应用：**CPU 均值/峰值**、**堆使用率**、**Full GC 次数/间隔**、**HTTP 工作线程活跃数**。
- 数据：**MySQL 慢查询条数（阈值内）**、**连接池等待**；若有 Redis/MQ 则看连接与队列积压。
- 网关：**Nginx worker 连接**、**499/502/504 比例**。

## 3. 业务场景分组

| 分组 | 典型接口 | 说明 |
| --- | --- | --- |
| **G1 本地只读** | `/post/list`、`/post/get`、`/about/*`、`/links/list`、`/album/*` | 首页与内容浏览主路径，对延迟最敏感。 |
| **G2 管理端读** | `/admin/login`（低频）、`/admin/stats/dashboard`、`/admin/post/list`、`/admin/logs/list` | 可略放宽；登录与后续请求须分开统计。 |
| **G3 写入与埋点** | `/post/stats/track`、各类 POST/PUT/DELETE | 默认不纳入只读容量；若启用须单独定标。 |

## 4. 分级标准（S / A / B）

在**约定并发与时长**下，按 **错误率 + G1 P95** 综合定级（取较差一档为准）。

### 4.1 只读（G1）— 核心标准

| 等级 | 全局错误率 | G1 接口 P95 | G1 接口 P99 | 说明 |
| --- | --- | --- | --- | --- |
| **S** | ≤ 0.1% | ≤ 200 ms | ≤ 800 ms | 可对外宣称的优质体验。 |
| **A** | ≤ 0.5% | ≤ 300 ms | ≤ 1500 ms | **默认生产目标**；与历史报告 SLA 对齐。 |
| **B** | ≤ 2.0% | ≤ 800 ms | ≤ 3000 ms | 可接受但须排期优化；新上线过渡期可用。 |
| **不合格** | 任意一项劣于 B | — | — | 禁止作为大促或宣发基线；须先治理再复测。 |

### 4.2 管理端读（G2）

| 等级 | 全局错误率（该场景内） | G2 接口 P95 |
| --- | --- | --- |
| **S** | ≤ 0.5% | ≤ 500 ms |
| **A** | ≤ 1.0% | ≤ 800 ms |
| **B** | ≤ 2.0% | ≤ 1500 ms |

### 4.3 资源红线（与分级同时观测，触发任一须记录为风险）

| 资源 | 建议红线（压测窗口内） |
| --- | --- |
| 应用 CPU | 持续 5 分钟均值 **&gt; 85%** 或单核打满导致延迟陡升 |
| 堆内存 | **&gt; 85%** 老年代长期居高或 Full GC 间隔 &lt; 5 分钟 |
| MySQL | 连接池 **等待队列持续非空** 或慢查询（按实例阈值）突增 |
| 网关 | **502/504** 占比 &gt; 0.1% 或连接超时集中爆发 |

### 4.4 压测端限制 vs 服务端容量（定标建议）

为避免把“压测机侧限制”误判为“服务端极限”，建议区分：

- **对内（回归）**：本地单机压测主要用于对比版本趋势。
- **对内（容量上限）**：用分布式压测或调优压测机网络栈后再定标 **S 档最大并发**。

## 5. 阶梯压测与达标判定

### 5.1 推荐阶梯（只读）

每阶 **Ramp-Up 60～180 s**，**Hold ≥ 900 s**（或至少 600 s），并发示例：

| 阶段 | 并发（threads） | 目的 |
| --- | ---: | --- |
| L0 | 5～10 | 脚本与环境冒烟 |
| L1 | 20 | 基线 |
| L2 | 40 | 中间容量 |
| L3 | 60 | 逼近拐点 |
| L4 | 80 | 当前基线（本地已验证通过 S） |
| L5 | 120 | 用于二分定位 S 上限（80 与更高档之间） |
| L6 | 160 | 压测机压力上探（可能触发 `BindException`） |

每阶输出独立 **JTL + JMeter HTML Dashboard**，并记录本节分级结果。

### 5.2 达标判定

- 在目标阶（如 L4）达到 **G1 等级 A 及以上**，且资源未触发红线，则认定**当前容量下满足生产性能标准**。
- 若仅在 L1/L2 达标、L3/L4 降级，则对外容量表述为：**「在 A 级 SLA 下建议并发 ≤ L2」**，并列出瓶颈类型（网关/应用/DB）。

### 5.2.1 结论写作模板（推荐）

建议所有阶段报告统一使用以下模板，便于横向对比：

1. **结论**：在 `<环境>` + `<负载模型>` + `<时长>` 下，`<并发区间>` 满足 `<等级>`。
2. **边界**：`<下一档>` 因 `<error/P95/P99/资源>` 超阈值，不满足 `<等级>`。
3. **风险**：是否出现压测端异常（如 `BindException`）或数据口径偏差。
4. **建议值**：对外保守并发建议 = `最大通过档位 × 0.7~0.8`（可按业务风险偏好调整）。

### 5.3 测定「G1-S 档」下最大并发（JMeter + 官方 HTML 报告）

目标：在 **第 1.1 节环境规格** 与 **固定压测时长** 下，找到满足 **4.1 节 S 档**（全局错误率 ≤0.1%，且每个 G1 接口 P95≤200ms、P99≤800ms）的 **最大 `-Jthreads`**。

**步骤概要**

1. 固定参数（与正式结论可比）：`hold_sec` 建议 **600～900**；`ramp_up_sec` 建议 **60～180**；仅开 **TG01 只读**（`track`、管理端、写场景保持关闭）。
2. 从较低并发开始阶梯加压，并使用 **二分法** 加速收敛：例如先跑 `80` 与 `160`，若 `80` 通过、`160` 失败，则再跑 `120`，依次缩小区间。
3. 每档在 Dashboard 中查看：
   - **Errors**：全局错误率是否 ≤ **0.1%**；
   - **Statistics** / **Response Times** / 各 **Transaction** 的百分位：五个 G1 请求（脚本中 label 为 `Public /post/list` 等）是否均满足 **P95≤200ms、P99≤800ms**。
4. **最大并发** = 「仍满足 S 档」的最高一档；下一档若任一 G1 接口或全局错误率突破阈值，则容量上界取上一档，并在报告中写明**突破项**（例如错误率、或某一接口 P95）。
### 5.4 判档口径提醒（Total vs 每接口）

- **正式 S 判档以“每接口”优先**：即使 Total P95≤200ms，只要任一 G1 接口 P95>200ms，也应判为 **S 不通过**。
- 若仅用于粗略摸底，可先看 Total（更快），但报告里必须明确标注“Total 口径”。

5. **异常判定**：若失败样本的 `responseCode` 主要为 `Non HTTP response code: java.net.BindException`，通常表示**压测机侧临时端口耗尽**，该档不用于判定服务端容量上限，应先解决压测机侧问题（更换压测机/分布式/调优网络栈/确保 Keep-Alive）。

**单档命令示例（PowerShell，单行；请替换输出路径）**

```powershell
jmeter -n -t "performance/jmeter/ayeezblog-performance-test.jmx" `
  -Jprotocol=http -Jhost=localhost -Jport=8080 -Jbase_path="" `
  -Jthreads=80 -Jramp_up_sec=120 -Jhold_sec=900 `
  -Jwrite_threads=0 `
  -l "performance/jmeter/results/s-tier-probe-threads80-900s.jtl" `
  -e -o "performance/jmeter/reports/s-tier-probe-threads80-900s"
```

每档结束后打开对应目录下的 `index.html` 即可判档，无需 Python 或其它后处理脚本。若需归档原始 `.jtl`，请遵守仓库 `.gitignore` 策略（大文件可不提交，仅保留报告截图与结论表）。

**粗测与精测（可选）**

- **粗测**：`hold_sec` 用 **180～300** 快速缩小 `threads` 区间（结论标注为粗测）。
- **精测**：对最终相邻两档用 **600～900** 各跑一轮，以精测结果写入正式报告。

**当前项目本地压测结果摘要（2026-04-17，hold=900s，S 档二分进行中）**

- `threads=220`：错误率 `0%`，Total P95≈`28ms`、P99≈`65ms`（满足 S）。
- `threads=250`：错误率 `0%`，Total P95≈`40ms`、P99≈`71ms`（满足 S）。
- `threads=265`：错误率 `0%`，Total P95≈`78ms`、P99≈`149.99ms`（满足 S）。
- `threads=272`：错误率 `0%`，Total P95≈`97.95ms`、P99≈`190ms`（满足 S）。
- `threads=276`：错误率 `0%`，Total P95≈`164ms`、P99≈`263ms`（满足 S）。
- `threads=278`：错误率 `0%`，Total P95≈`193ms`、P99≈`370.99ms`（满足 S）。
- `threads=279`：错误率 `0%`，Total P95≈`133.95ms`、P99≈`237ms`；但接口维度 `Public /post/list` P95≈`204ms` 超过阈值，严格 S 不通过。
- `threads=280`：错误率 `0%`，但 Total **P95≈243ms**（不满足 S 的 P95≤200ms）。综合判定：**严格 S 最大并发 = 278**。

## 6. 发布与回归门禁（建议）

| 触发条件 | 最低要求 |
| --- | --- |
| 每次后端发版（影响 API） | L1 或 L2 跑满 10～15 分钟，**G1 不低于 B**，无新增资源红线 |
| 重大重构 / 网关变更 | 完整阶梯 L0～L4，**G1 不低于 A** |
| 季度或容量承诺前 | 浸泡 + 可选突刺，结论写入 `AyeezBlog-性能分析报告.md` |
