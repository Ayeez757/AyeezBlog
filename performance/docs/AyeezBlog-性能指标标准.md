# AyeezBlog 性能指标标准

本文档定义 AyeezBlog 在压测与线上观测中应遵循的性能指标、分级阈值与验收口径，便于版本对比、回归门禁与容量规划。

---

## 1. 适用范围与前提

| 维度 | 说明 |
| --- | --- |
| 环境 | **预发 / 生产** 结论可互相引用，但须在报告中标明环境；本地压测仅作开发调试，不作为 SLA 依据。 |
| 协议与入口 | 公网场景以 **HTTPS + 域名 + `/api` 前缀** 为准；直连容器 IP 仅作排障对照。 |
| 负载模型 | 与 `performance/jmeter/ayeezblog-performance-test.jmx` 中线程组一致时需注明：只读公网、是否含管理端、是否含写入。 |
| 时长 | **基线** ≥ 10 分钟；**容量/回归** ≥ 15 分钟；**浸泡** ≥ 60 分钟（可选）。 |
| 数据 | 生产压测默认 **只读**；含写入或埋点须在预发或专用数据集上执行并单独定标。 |

### 1.1 被测服务器规格（当前压测基线）

以下规格为**当前公网压测所对应的服务器配置**，写入报告与标准时需一并注明，避免不同硬件下结论不可比。

| 项目 | 规格 |
| --- | --- |
| CPU | **2 核**（vCPU） |
| 内存 | **4 GB** |
| 公网带宽 | **峰值约 5 Mbps**（与其它文档、云厂商「5M 带宽」类表述对齐时，默认按 **5 兆比特每秒**理解；若控制台单位为 MB/s 或其它，以云厂商说明为准并换算后写入报告） |

> 说明：在 **2C4G + 5 Mbps 峰值带宽** 下，公网压测的瓶颈常出现在 **网络与连接层**（带宽与 TLS/并发连接），与单机 CPU 标称核数并非简单线性关系。

### 1.2 压测发起位置（与结论强绑定）

同一套 G1 指标，**压测客户端所在网络不同，结论不可混用**：

| 发起位置 | 典型用途 | 对 G1-S 的含义 |
| --- | --- | --- |
| **本地 PC → 公网域名（HTTPS）** | 模拟真实用户端到端体验 | 含本地出网、公网抖动、TLS；**长尾与错误往往由链路主导**，未必能反映应用单机极限。 |
| **云上同地域 ECS → 公网/VPC 入口** | 剥离本地网络噪声，侧向服务端与网关容量 | 更接近「系统侧」能力；**建议用于测定 S 档最大并发**（见 4.4 节）。 |
| **内网直连应用端口（无 Nginx）** | 纯应用与 DB 对比 | 仅作开发/排障对照，**不作为公网 SLA**。 |

**项目实测结论（2026-04-15，本地 JMeter → `https://blog.ayeez.cn/api`，`hold_sec=900`）**：在 **5～63** 线程多档精测下，**G1-S 档（P95≤200ms、P99≤800ms、全局错误率≤0.1%）始终未能同时满足**；低并发（如 5 线程）仍出现 **P95 约 400～1100ms 级** 的长尾。因此：**不宜以当前「本地→公网」结果宣称达到 G1-S**；对外容量承诺建议以 **G1-A** 为主，G1-S 改在 **同地域压测源** 上重测后再定标（定标分层见 4.4 节）。

## 2. 指标分类与统一定义

### 2.1 吞吐（Throughput）

- **RPS**：每秒完成的采样请求数（与 JMeter Dashboard 中 Throughput 一致）。
- **业务吞吐**：可按接口维度统计，用于识别热点接口。

### 2.2 时延（Latency）

- **Avg**：算术平均响应时间（易受长尾拉高，仅作辅助）。
- **P50 / P90 / P95 / P99**：按单次请求耗时升序取分位数；**对外承诺以 P95 为主，稳定性以 P99 与 Max 为辅**。
- 口径：从 JMeter 发起至收到完整响应（含 TLS、网关、应用、数据库）；与 `elapsed` 字段一致。

### 2.3 成功率与错误率

- **成功**：HTTP 2xx 且业务体满足约定（如 JSON 中 `code=200`），与脚本断言一致。
- **错误率** = 失败样本数 / 总样本数 × 100%。  
- **HTTP 非 2xx**、**连接/读超时**、**断言失败** 均计入错误率。

### 2.4 可用性与稳定性（可选但推荐）

- **连续错误窗口**：在滑动 1 分钟内错误率持续 > 1% 视为不稳定，用于浸泡测试。
- **雪崩**：错误率在 5 分钟内从 &lt;0.5% 升至 &gt;5% 且无恢复，记为不合格。

### 2.5 资源与饱和度（与压测报告配套）

在服务器侧同步采集（至少压测窗口内）：

- 应用：**CPU 均值/峰值**、**堆使用率**、**Full GC 次数/间隔**、**HTTP 工作线程活跃数**。
- 数据：**MySQL 慢查询条数（阈值内）**、**连接池等待**；若有 Redis/MQ 则看连接与队列积压。
- 网关：**Nginx worker 连接**、**499/502/504 比例**。

## 3. 业务场景分组

| 分组 | 典型接口 | 说明 |
| --- | --- | --- |
| **G1 公网只读** | `/api/post/list`、`/api/post/get`、`/api/about/*`、`/api/links/list`、`/api/album/*` | 首页与内容浏览主路径，对延迟最敏感。 |
| **G2 管理端读** | `/api/admin/login`（低频）、`/api/admin/stats/dashboard`、`/api/admin/post/list`、`/api/admin/logs/list` | 可略放宽；登录与后续请求须分开统计。 |
| **G3 写入与埋点** | `/api/post/stats/track`、各类 POST/PUT/DELETE | 默认不在生产压测；若启用须单独定标并控制数据污染。 |

## 4. 分级标准（S / A / B）

在**约定并发与时长**下，按 **错误率 + G1 P95** 综合定级（取较差一档为准）。

### 4.1 公网只读（G1）— 核心标准

| 等级 | 全局错误率 | G1 接口 P95 | G1 接口 P99 | 说明 |
| --- | --- | --- | --- | --- |
| **S** | ≤ 0.1% | ≤ 200 ms | ≤ 800 ms | 可对外宣称的优质体验。 |
| **A** | ≤ 0.5% | ≤ 300 ms | ≤ 1500 ms | **默认生产目标**；与历史报告 SLA 对齐。 |
| **B** | ≤ 2.0% | ≤ 800 ms | ≤ 3000 ms | 可接受但须排期优化；新上线过渡期可用。 |
| **不合格** | 任意一项劣于 B | — | — | 禁止作为大促或宣发基线；须先治理再复测。 |

### 4.2 管理端读（G2）

| 等级 | 全局错误率（该场景内） | G2 接口 P95 |
| --- | --- | --- |
| **S** | ≤ 0.5% | ≤ 500 ms |
| **A** | ≤ 1.0% | ≤ 800 ms |
| **B** | ≤ 2.0% | ≤ 1500 ms |

### 4.3 资源红线（与分级同时观测，触发任一须记录为风险）

| 资源 | 建议红线（压测窗口内） |
| --- | --- |
| 应用 CPU | 持续 5 分钟均值 **&gt; 85%** 或单核打满导致延迟陡升 |
| 堆内存 | **&gt; 85%** 老年代长期居高或 Full GC 间隔 &lt; 5 分钟 |
| MySQL | 连接池 **等待队列持续非空** 或慢查询（按实例阈值）突增 |
| 网关 | **502/504** 占比 &gt; 0.1% 或连接超时集中爆发 |

### 4.4 公网体验 vs 系统容量（定标建议）

为避免「S 档在公网永远测不到」与「系统其实仍健康」的矛盾，建议区分：

- **对外（用户感知）**：以 **G1-A**（或经业务同意的放宽阈值）作为博客类公网服务的默认承诺口径。
- **对内（容量/优化）**：以 **同地域压测** 得到的 **G1-S 或 G1-A 最大并发** 作为扩容与网关调参依据。

## 5. 阶梯压测与达标判定

### 5.1 推荐阶梯（公网只读）

每阶 **Ramp-Up 60～120 s**，**Hold ≥ 900 s**（或至少 600 s），并发示例：

| 阶段 | 并发（threads） | 目的 |
| --- | ---: | --- |
| L0 | 5～10 | 脚本与环境冒烟 |
| L1 | 20 | 基线 |
| L2 | 40 | 中间容量 |
| L3 | 60 | 逼近拐点 |
| L4 | 80 | 当前脚本上限或目标容量 |

每阶输出独立 **JTL + JMeter HTML Dashboard**，并记录本节分级结果。

### 5.2 达标判定

- 在目标阶（如 L4）达到 **G1 等级 A 及以上**，且资源未触发红线，则认定**当前容量下满足生产性能标准**。
- 若仅在 L1/L2 达标、L3/L4 降级，则对外容量表述为：**「在 A 级 SLA 下建议并发 ≤ L2」**，并列出瓶颈类型（网关/应用/DB）。

### 5.3 测定「G1-S 档」下最大并发（仅用 JMeter + 官方 HTML 报告，无需脚本）

目标：在 **第 1.1 节服务器规格** 与 **固定压测时长** 下，找到满足 **4.1 节 S 档**（全局错误率 ≤0.1%，且每个 G1 接口 P95≤200ms、P99≤800ms）的 **最大 `-Jthreads`**。

**步骤概要**

1. 固定参数（与正式结论可比）：`hold_sec` 建议 **600～900**；`ramp_up_sec` 建议 **60～120**；仅开 **TG01 公网只读**（`track`、管理端、写场景保持关闭）。
2. 从较低并发开始阶梯加压，例如：`5 → 10 → 15 → 20 → 30 → 40 …`，每档单独生成 **`.jtl` + `-e -o` 官方 Dashboard**（目录勿复用，需为空目录）。
3. 每档在 Dashboard 中查看：
   - **Errors**：全局错误率是否 ≤ **0.1%**；
   - **Statistics** / **Response Times** / 各 **Transaction** 的百分位：五个 G1 请求（脚本中 label 为 `Public /post/list` 等）是否均满足 **P95≤200ms、P99≤800ms**。
4. **最大并发** = 「仍满足 S 档」的最高一档；下一档若任一 G1 接口或全局错误率突破阈值，则容量上界取上一档，并在报告中写明**突破项**（例如错误率、或某一接口 P95）。

**单档命令示例（PowerShell，单行；请替换输出路径）**

```powershell
jmeter -n -t "performance/jmeter/ayeezblog-performance-test.jmx" "-Jprotocol=https" "-Jhost=blog.ayeez.cn" "-Jport=443" "-Jbase_path=/api" "-Jthreads=20" "-Jramp_up_sec=90" "-Jhold_sec=600" "-l" "performance/jmeter/results/s-tier-probe-threads20.jtl" "-e" "-o" "performance/jmeter/reports/s-tier-probe-threads20"
```

每档结束后打开对应目录下的 `index.html` 即可判档，无需 Python 或其它后处理脚本。若需归档原始 `.jtl`，请遵守仓库 `.gitignore` 策略（大文件可不提交，仅保留报告截图与结论表）。

**粗测与精测（可选）**

- **粗测**：`hold_sec` 用 **180～300** 快速缩小 `threads` 区间（结论标注为粗测）。
- **精测**：对最终相邻两档用 **600～900** 各跑一轮，以精测结果写入正式报告。

**当前项目已执行到的经验区间（2026-04-15，本地 → 公网，精测 `hold_sec=900`）**

以下数据来自 JMeter 官方 Dashboard **Statistics** 中 **Total** 行（Dashboard 中百分位列名多为 **90th / 95th / 99th**，与本文 P95/P99 对应；各 G1 接口分位普遍同量级或更差）：

| threads | 全局错误率 | Total P95 (ms) | Total P99 (ms) | 相对 G1-S |
| ---: | ---: | ---: | ---: | --- |
| 5 | 0% | 675 | 1168 | **不满足**（延迟） |
| 10 | 0.136% | 414 | 1152 | **不满足**（错误率 + 延迟） |
| 20 | 0.043% | 723 | 1560 | **不满足**（延迟） |
| 40 | 0.014% | 503 | 1154 | **不满足**（延迟） |
| 60 | 0.056% | 1131 | 1171 | **不满足**（延迟） |

## 6. 发布与回归门禁（建议）

| 触发条件 | 最低要求 |
| --- | --- |
| 每次后端发版（影响 API） | L1 或 L2 跑满 10～15 分钟，**G1 不低于 B**，无新增资源红线 |
| 重大重构 / 网关变更 | 完整阶梯 L0～L4，**G1 不低于 A** |
| 季度或容量承诺前 | 浸泡 + 可选突刺，结论写入 `AyeezBlog-性能分析报告.md` |
