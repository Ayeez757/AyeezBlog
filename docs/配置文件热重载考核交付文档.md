## 1. 交付目标

本项目完成考核 `Level 1：配置文件热重载`。  
实现目标如下：

- 在服务不停机的前提下，动态加载新的运行时配置；
- 配置更新后可真实影响后续请求行为（前端可观察到分页条数变化）；
- 配置加载失败时保持上一版配置继续服务，不发生服务中断。

> 评审说明：  
> 验收以「热重载行为可复现」为准：**优先**使用 `deploy/review` Docker 栈（从克隆到可访问的完整步骤见第 4 节 **4.0.1**）。亦可使用本地 MySQL + 后端（**4.0.2**）。功能验证仍以 **4.1～4.2**（及 Level2 相关小节）为准。

## 2. 实现范围与核心设计

### 2.1 实现范围

本次交付实现了level1和level2的功能演示，（外部插件 jar 动态加载并切换当前规则实现），用于展示“逻辑热替换”的关键链路。

level2的资源释放、副作用回收完成了一部分，单一插件（不对其他插件造成副作用）反复加载卸载的产生的资源能够成功释放，但是无法做到多个互相影响的插件副作用逆序回收。

### 2.2 核心设计

为保证运行期间配置切换的安全性与可观测性，新增以下核心模块（我放在了`AyeezBlog-Backend/blog-server/src/main/java/cn/ayeez/blogserver/runtime/plugin`）：

- `RuntimeConfig`：运行时配置快照对象；
- `RuntimeConfigLoader`：负责配置文件读取与校验；
- `RuntimeConfigManager`：使用 `AtomicReference<RuntimeConfig>` 保存当前生效配置，支持原子切换；
- `RuntimeConfigWatchService`：基于 `WatchService` 监听配置文件变更并自动触发重载；
- `RuntimeConfigDemoController`：提供重载触发与验证接口。

### 2.3 配置切换策略

配置切换采用“先加载并校验、再原子替换”的策略

实现原理如下：

1. **触发阶段（自动）**
  - 自动触发：`RuntimeConfigWatchService` 监听到 `runtime-config.yml` 保存事件后触发重载；
  - 监听事件最终收敛到统一重载链路（`RuntimeConfigManager.reload()`）。
2. **加载阶段（不影响当前服务）**
  - `RuntimeConfigLoader` 从目标路径读取 YAML 并反序列化为新的 `RuntimeConfig` 候选对象；
  - 此时只是“候选配置”，尚未替换当前在线配置，对外请求仍读取旧快照。
3. **校验阶段（失败即终止）**
  - 执行字段完整性与业务约束校验（例如 `postPageSize` 取值范围、插件 ID 合法性）；
  - 任何校验失败都直接返回失败，不进入替换阶段。
4. **生效阶段（原子替换）**
  - 校验通过后，`RuntimeConfigManager` 通过 `AtomicReference<RuntimeConfig>` 一次性替换当前配置引用；
  - 原子替换保证并发请求下不会出现“半更新状态”：请求要么读到旧配置，要么读到新配置。
5. **请求可见性与回退语义**
  - 替换完成后，仅影响后续请求；已在执行中的请求继续使用其读取时拿到的配置快照；
  - 当加载或校验失败时，`AtomicReference` 不发生写入，系统继续使用上一版稳定配置，形成天然失败回退。

该策略在实现上同时满足了：不停机、并发安全、失败不扩散、行为可预测。

## 3. 配置文件与接口说明

### 3.1 配置文件

运行时配置文件：

- 开发/本地默认：`AyeezBlog-Backend/blog-server/src/main/resources/runtime-config.yml`
- **评审 Docker（推荐）**：宿主机 `deploy/review/runtime-config.yml` 挂载到容器内 `/app/config/runtime-config.yml`，环境变量 `RUNTIME_CONFIG_PATH` 指向该路径；修改宿主机文件即可触发 WatchService。
- 生产博客（非考核）：可外置挂载 `deploy/prod/runtime-config.yml` 等，容器内同样为 `/app/config/runtime-config.yml`（与生产 compose 配套使用）。

当前示例字段：

- `postPageSize`：文章分页大小；
- `strictModeEnabled`：严格模式开关（开启后业务分页优先使用运行时配置值）。

### 3.2 演示接口

用于热重载验证的接口如下：（有保留手动切换的接口，但是现在能自动监听，所以就没必要测这几个了，你只需要改完配置文件之后去前端看效果就行）

- `GET /post/runtime/config`：查看当前生效配置；
- `POST /post/runtime/reload-config`：手动触发配置重载；
- `GET /post/runtime/reload-config`：兼容浏览器调试；
- `GET /post/runtime/demo-cards`：演示配置变化对业务响应的影响。

自动触发机制：

- `WatchService` 监听 `runtime-config.yml` 文件变化；
- 保存配置文件后自动调用 `RuntimeConfigManager.reload()`；
- 含防抖策略，避免一次保存触发多次重复重载。
- 评审/生产容器内通过 `RUNTIME_CONFIG_PATH=/app/config/runtime-config.yml` 指向挂载文件时，WatchService 同样监听该路径并自动重载。

业务联动接口：

- `GET /post/list`：分页行为会受运行时配置影响（严格模式开启时可直接观察变化）。（也可以去前端看效果，严格模式关闭的话会根据前端的请求是否自带合法的分页参数来决定是否遵循配置文件的分页参数；若走前端代理网关，请求路径通常会表现为 `/api/post/list`）

## 4. 验证过程与结果

评审建议：

- 部署任选 **4.0.1（Docker，推荐）** 或 **4.0.2（本地）**；
- 功能验收仅需复现 **4.1～4.2**（自动重载 / 自动触发失败回退），即可确认 Level 1 要求。

### 4.0 评审准备（Level1/Level2 通用）

为便于观察分页效果，建议评审在开始验证前先具备数据库中的演示数据（Level1 也需要用到）。

#### 4.0.1 部署方式一：Docker 评审栈（推荐）

目的：评审机仅需安装 **Docker Engine** 与 **Docker Compose**（Windows 上推荐 **Docker Desktop**），无需单独安装 MySQL、JDK 或 Maven；后端镜像在容器构建阶段由多阶段 `Dockerfile.backend` 完成 Maven 打包。

**前置条件**

- 已安装 Docker，且命令 `docker compose version`（或 `docker-compose version`）可用。
- 磁盘与网络：首次 `up --build` 会拉取基础镜像并在容器内执行 `mvn package`，需预留一定磁盘空间；需能访问 Maven Central（构建阶段）。
- **工作目录**：以下路径均以「已 `git clone` 的仓库根目录」为当前目录；`docker-compose.yml` 使用相对路径挂载仓库根下的 `AyeezBlog建表.sql`、`docs/sql/review-seed-posts.sql`，**请务必在仓库内启动**，勿只拷贝 `deploy/review` 子目录到无仓库上下文的位置（否则挂载失败）。

**完整部署流程（按顺序执行）**

1. **获取源码**  
   `git clone <本仓库地址>` 并 `cd AyeezBlog`（或你的本地克隆根目录名）。

2. **进入评审 Compose 目录**  
   `cd deploy/review`

3. **（推荐）准备环境变量文件**  
   - Windows（PowerShell）：`Copy-Item .env.example .env`  
   - Linux / macOS：`cp .env.example .env`  
   - 用编辑器打开 `.env`，按需修改：
     - `MYSQL_ROOT_PASSWORD`、`HM_DB_USER`、`HM_DB_PASSWORD`（与 compose 内 MySQL 用户一致即可）；
     - `HM_JWT_SECRET_KEY`（建议自行更换为足够长的随机串）；
     - 若本机 **8080 / 8888 / 33060** 已被占用，修改 `REVIEW_BACKEND_PORT`、`REVIEW_NGINX_PORT`、`REVIEW_MYSQL_PORT`。  
   - 不复制 `.env` 也可启动：compose 内已为各变量提供默认值，与 `.env.example` 一致。

4. **首次构建并启动全栈**  
   `docker compose up --build`  
   - 首次会构建 `backend` 镜像（内含 Maven 下载依赖与打包），耗时可能 **数分钟～十余分钟**，属正常情况。  
   - 待日志中出现 Spring Boot 启动完成、且 `nginx` 容器已启动，表示链路就绪。

5. **等待健康检查通过（首次尤甚）**  
   - MySQL 首次初始化需执行建表与种子 SQL；后端 `healthcheck` 在 `start_period` 内轮询 **8080** 端口。  
   - 若 `nginx` 长时间未起，多为 `backend` 尚未 healthy：请先看 `backend` 容器日志，勿急于判定失败。

6. **启动后自检（浏览器或 curl）**  
   - 经 Nginx（默认端口 **8888**）：访问 `http://localhost:8888/post/list?pageNum=1&pageSize=10`（或你修改后的 `REVIEW_NGINX_PORT`）。  
   - 直连后端（默认 **8080**）：`http://localhost:8080/post/list?pageNum=1&pageSize=10`。  
   - 查看运行时配置：`GET http://localhost:8888/post/runtime/config`（或对应后端端口）。  
   - 返回 JSON 且列表有数据（含 `review-post-*`），即表示 **MySQL + 后端 + 反代** 正常。

7. **热重载文件位置（宿主机侧，与容器同步）**  
   - **Level 1**：编辑 `deploy/review/runtime-config.yml` 并保存（已挂载到容器 `/app/config/runtime-config.yml`，`RUNTIME_CONFIG_PATH` 已配置）；保存后由 WatchService 自动重载，验证见 **4.1、4.2**。  
   - **Level 2 外部 jar**：将插件 jar 投放到 `deploy/review/plugins/page-size/`（挂载到 `/app/plugins/page-size`），详见 **7.5.2**。

8. **（可选）与 PowerShell 压测脚本联调**  
   - 在仓库根目录执行脚本，并显式指定服务地址与插件目录，例如：  
     `-BaseUrl "http://localhost:8888"`（经 Nginx）或 `-BaseUrl "http://localhost:8080"`（直连）；  
     `-PluginDir "deploy/review/plugins/page-size"`（与上一步目录一致）。  
   - 详见 **7.5.3**。

**服务与默认端口一览**

| 服务 | 容器内 | 宿主机默认（可在 `.env` 修改） | 说明 |
|------|--------|-------------------------------|------|
| MySQL | 3306 | `33060` → `REVIEW_MYSQL_PORT` | 首次初始化执行 `AyeezBlog建表.sql` + `review-seed-posts.sql` |
| 后端 Spring Boot | 8080 | `8080` → `REVIEW_BACKEND_PORT` | `SPRING_PROFILES_ACTIVE=review` |
| Nginx | 80 | `8888` → `REVIEW_NGINX_PORT` | 反代到 `backend:8080` |

**栈内行为摘要**

- **MySQL**：数据在 Compose 命名卷 `mysql_review_data`；仅**首次**创建数据目录时执行 `docker-entrypoint-initdb.d` 下 SQL。若需**重新初始化库表**，见下文「数据重置」。  
- **后端**：配置见 `AyeezBlog-Backend/blog-server/src/main/resources/application-review.yml`。**不连接 RabbitMQ**（已排除自动配置）。**DeepSeek / 火山即梦封面**由 `HM_FEATURE_DEEPSEEK`、`HM_FEATURE_VOLCENGINE_COVER` 控制，默认 `false`；**七牛**四项环境变量留空即不启用。  
- **Nginx**：对外提供统一入口，便于与「仅测后端」场景一致地使用 80 反代路径习惯。

**可选能力（默认关闭）如何开启**

在 `deploy/review/.env` 中按需设置（变量含义与示例见同目录 `.env.example`）：

- **DeepSeek 文章简介**：`HM_FEATURE_DEEPSEEK=true` 且配置有效 `DEEPSEEK_API_KEY`。  
- **火山即梦封面**：`HM_FEATURE_VOLCENGINE_COVER=true` 且配置 `VOLCENGINE_ACCESS_KEY`、`VOLCENGINE_SECRET_KEY`（封面转存通常还需七牛）。

## 7. 业务逻辑热重载实现原理

本项目的业务逻辑热重载实现方式是：把“会变化的业务规则”抽象为插件，由规则引擎在运行时托管当前插件实例，从而实现“主流程不改、规则可切换”。

核心执行链路如下：

1. 请求进入业务层后，`PostServerImpl` 不再直接写死分页规则，而是委托 `PageSizeRuleEngineService` 计算最终分页参数；
2. 规则引擎持有当前生效插件引用（内置插件或外部插件），并将请求参数封装为 `PageSizeRuleInput` 交给插件执行；
3. 插件返回 `PageSizeRuleOutput`（包含生效分页值与命中原因），业务层据此继续查询，Controller 无需感知插件来源；
4. 当发生热更新（目录监听自动加载）时，引擎按“先 `init` 新插件（插件登记资源）-> 再切换当前引用 -> 最后 `dispose` 旧插件并触发平台统一回收 + 关闭旧 `ClassLoader`”的顺序完成替换；
5. 若新插件加载或切换失败，则保持旧插件继续服务，避免业务中断或切到不可用状态；
6. 切换后的效果会直接体现在后续请求上，并可通过当前插件状态与切换历史接口观察。

### 7.1 新增结构

新增规则插件相关模块：

- `RulePlugin<I, O>`：统一插件接口（`id / init / execute / dispose`）
- `PluginContext`：主系统提供的受控依赖边界
- `PageSizeRuleInput` / `PageSizeRuleOutput`：分页规则输入输出对象
- `DefaultPageSizeRulePlugin`：默认分页规则实现
- `RuntimeOnlyPageSizeRulePlugin`：运行时优先分页规则实现
- `PageSizeRuleEngineService`：规则引擎服务，负责委托插件执行

### 7.2 当前能力

已实现外置插件链路：外部插件 jar 自动加载、目录监听自动热加载、失败保持当前插件继续服务。

### 7.3 外部插件 jar 自动加载与切换（Level 2 基础能力演示）

在现有运行时插件切换能力基础上，已补充“监听目录自动加载外部插件 jar 并切换”的基础能力，具体包括：

- 新增 `ExternalPageSizePluginLoader`，负责从外部 jar 通过 `URLClassLoader` 动态加载插件类；
- 新增 `ExternalPageSizePluginLoadResult`，封装外部插件实例、类加载器、jar 路径与主类名；
- 规则引擎新增切换到外部插件的方法，支持在服务运行中将当前插件替换为 jar 中的新实现；
- 切换过程采用“先初始化新插件，再替换当前引用，最后释放旧插件并关闭旧外部类加载器”的顺序；

当前这部分能力属于 **Level 2 的基础版实现（自动监听路径）**：

### 7.4 外部插件演示模块

为方便本地演示，后端父工程下新增了 `blog-plugin-demo` 模块，用于单独产出一个外部插件 jar。

该模块特点如下：

- 打包产物不会重新包含宿主接口定义，避免类加载类型不一致问题；
- 当前内置了一个演示插件：`cn.ayeez.blogplugindemo.paging.DoublePageSizeRulePlugin`。

该演示插件的行为很简单：

### 7.5 外部插件自动热加载（插件目录监听）

在“外部插件 jar 动态加载与切换”的基础上，补充了**自动化触发**能力：当插件目录下的 `.jar` 发生变更时，后端会自动加载最新 jar 并切换当前插件，实现无需手动调用加载接口的逻辑热更新演示。

实现要点：

- 插件目录解析优先级：`PAGE_SIZE_PLUGIN_DIR`（环境变量） > `-Dpage.size.plugin.dir`（JVM 参数） > 默认目录 `plugins/page-size`；
- 后端启动后使用 `WatchService` 监听该目录的文件变更事件（创建/修改/删除）；
- 对保存/上传产生的高频事件做防抖处理；
- 对“半写入 jar”做稳定性检查（短时间内文件大小不再变化才尝试加载）；
- 自动选择目录内“最近一次修改时间最新”的 `.jar` 作为候选；
- 加载失败时保持当前插件继续服务（不影响业务可用性）；
- 切换成功后可通过接口查询当前来源与切换历史。
- 插件资源回收采用“插件登记 + 平台统一回收”机制：插件在 `init` 阶段通过 `PluginContext.registerCleanupAction(...)` 登记自身创建的可回收资源（如线程池、定时任务等）；
- 规则引擎在插件下线阶段按“先 `dispose` 旧插件，再执行平台登记的清理动作，最后关闭旧 `ClassLoader`”顺序回收资源，避免切换窗口中的资源悬挂；
- 是否执行平台回收由运行时配置 `runtime-config.yml` 中 `pluginCleanupEnabled` 控制（`true` 执行回收，`false` 跳过回收用于 A 组残留对照）；
- 外部插件初始化失败时，引擎会对“新插件半初始化资源 + 新 `ClassLoader`”执行即时清理，避免失败路径残留。

能力边界说明：

- 当前版本已实现“插件登记 + 平台回收”的基础治理：切换后会调用旧插件 `dispose()`，并执行平台登记的回收动作与旧 `URLClassLoader.close()`；
- 这并不等价于“所有类型副作用 100% 覆盖”：若插件未按规范登记某些资源（如自建线程、监听器、ThreadLocal、静态缓存），仍可能存在残留风险；
- 因此本项目当前可证明“热替换流程可跑通、失败可回退、业务不中断”，但不宣称“插件卸载后所有副作用 100% 可逆归零”。

#### 7.5.1 插件元信息（plugin.properties）

为避免自动加载时还需要手动传入主类名，外部插件 jar 约定必须包含 `plugin.properties`：

- `plugin.id`：插件 ID（用于可读性与定位）
- `plugin.class`：插件主类全限定名（自动加载所需）
- `plugin.version`：插件版本（可选，建议提供）

示例：

```properties
plugin.id=double-page-size-rule
plugin.class=cn.ayeez.blogplugindemo.paging.DoublePageSizeRulePlugin
plugin.version=1.0.0
```

- 不清理也不影响本轮结论，因为后续脚本会用新生成的数据与报告直接覆盖同名文件。
- 为避免“脚本投放目录”和“后端监听目录”不一致，下面命令统一显式指定 **PluginDir**：
  - 本地后端：`-PluginDir "AyeezBlog-Backend/blog-server/plugins/page-size"`
  - **Docker 评审栈**：`-PluginDir "deploy/review/plugins/page-size"`，且脚本 `-BaseUrl` 使用 `http://localhost:8888` 或 `http://localhost:8080`（与 **4.0.1** 一致）。

可选清理命令：

- `powershell -ExecutionPolicy Bypass -File "scripts/review/cleanup-level2-review.ps1"`

1. 执行前置检查（每组开始前）：
  - 清理上组残留产物（可选，但跑完A组再跑B组的时候建议不要执行，否则会清掉A组数据）：`powershell -ExecutionPolicy Bypass -File "scripts/review/cleanup-level2-review.ps1"`
  - 确认插件目录存在：`New-Item -ItemType Directory -Force -Path "AyeezBlog-Backend/blog-server/plugins/page-size" | Out-Null`

2. 设置本组运行时回收开关（修改 `runtime-config.yml` 并保存）：
  - A 组：`pluginCleanupEnabled: false`
  - B 组：`pluginCleanupEnabled: true`
  - 注意：开始 B 组测试前，请先重启后端服务，避免 A 组测试的残留影响 B 组测试。
3. 执行 300 轮自动热加载循环：

  - `powershell -ExecutionPolicy Bypass -File "scripts/review/check-level2-leak-signals.ps1" -PluginDir "AyeezBlog-Backend/blog-server/plugins/page-size" -Samples 8 -IntervalSeconds 3 -ExerciseRounds 30 -PostRevertQuietSeconds 10`

**对照试验总结合论**

- A/B 两组都完成了同样的 300 轮自动热加载，功能链路均稳定；
