# 配置文件热重载考核交付文档

## 1. 交付目标

本项目完成考核 `Level 1：配置文件热重载`。  
实现目标如下：

- 在服务不停机的前提下，动态加载新的运行时配置；
- 配置更新后可真实影响后续请求行为（前端可观察到分页条数变化）；
- 配置加载失败时保持上一版配置继续服务，不发生服务中断。

> 评审说明：  
> 本项目已在**线上 CI/CD + Docker** 场景完成验证（见下文 Docker 场景验证与证据），但由于线上 CI/CD 流程高度定制化（密钥、服务器目录、卷/网络命名等依赖评审侧环境），**不要求评审复现线上发布流程**。  
> 请评审以“本地运行 + 本地热重载复现”为验收标准。

## 2. 实现范围与核心设计

### 2.1 实现范围

本次交付以 **Level 1：配置文件热重载** 为主，同时补充了 **Level 2 的基础能力演示**（外部插件 jar 动态加载并切换当前规则实现），用于展示“逻辑热替换”的关键链路。

### 2.2 核心设计

为保证运行期间配置切换的安全性与可观测性，新增以下核心模块：

- `RuntimeConfig`：运行时配置快照对象；
- `RuntimeConfigLoader`：负责配置文件读取与校验；
- `RuntimeConfigManager`：使用 `AtomicReference<RuntimeConfig>` 保存当前生效配置，支持原子切换；
- `RuntimeConfigWatchService`：基于 `WatchService` 监听配置文件变更并自动触发重载；
- `RuntimeConfigDemoController`：提供重载触发与验证接口。

### 2.3 配置切换策略

配置切换采用“先加载、后替换”的安全流程：

1. 读取配置文件并反序列化；
2. 执行业务校验（例如 `postPageSize` 取值范围）；
3. 校验通过后原子替换当前配置；
4. 任一步失败则保持旧配置不变。

该策略确保系统在配置异常时仍可继续服务。

## 3. 配置文件与接口说明

### 3.1 配置文件

运行时配置文件：

- `AyeezBlog-Backend/blog-server/src/main/resources/runtime-config.yml`
- Docker 部署推荐外置挂载文件：`deploy/prod/runtime-config.yml`
- 容器内路径：`/app/config/runtime-config.yml`

当前示例字段：

- `postPageSize`：文章分页大小；
- `strictModeEnabled`：严格模式开关（开启后业务分页优先使用运行时配置值）。

### 3.2 演示接口

用于热重载验证的接口如下：

- `GET /post/runtime/config`：查看当前生效配置；
- `POST /post/runtime/reload-config`：手动触发配置重载；
- `GET /post/runtime/reload-config`：兼容浏览器调试；
- `GET /post/runtime/demo-cards`：演示配置变化对业务响应的影响。

自动触发机制：

- `WatchService` 监听 `runtime-config.yml` 文件变化；
- 保存配置文件后自动调用 `RuntimeConfigManager.reload()`；
- 含防抖策略，避免一次保存触发多次重复重载。
- Docker 部署下通过 `RUNTIME_CONFIG_PATH=/app/config/runtime-config.yml` 指向挂载文件，容器内同样支持自动重载。

业务联动接口：

- `GET /api/post/list`：分页行为会受运行时配置影响（严格模式开启时可直接观察变化）。

## 4. 验证过程与结果

评审建议（本地复现优先）：

- 评审仅需复现 `4.1~4.3`（本地手动重载 / 自动重载 / 失败回退），即可确认 Level 1 要求；
- `4.5` 为线上补充验证，不作为评审复现要求。

### 4.1 手动触发重载验证

验证步骤：

1. 启动后端服务；
2. 将 `runtime-config.yml` 中 `postPageSize` 改为合法值（如 `3`）；
3. 调用 `POST /post/runtime/reload-config`；
4. 再次访问 `GET /api/post/list` 或前端首页文章列表。

验证结果：

- 接口返回与前端展示均体现新分页大小；
- 后续请求行为已发生变化，证明重载生效。

### 4.2 自动触发重载验证（WatchService）

验证步骤：

1. 启动后端服务（确保监听线程已启动）；
2. 直接修改 `runtime-config.yml` 合法配置（如 `postPageSize`）并保存；
3. 不调用任何重载接口，直接访问 `GET /post/runtime/config` 或前端列表页面。

验证结果：

- 配置变更可自动生效；
- 后续请求行为同步变化；
- 自动触发能力通过测试。

### 4.3 失败回退验证

验证步骤：

1. 将 `runtime-config.yml` 设置为非法值（如 `postPageSize: 0`）；
2. 调用 `POST /post/runtime/reload-config`。

实际返回：

```json
{
  "code": 400,
  "message": "重载失败：配置文件格式或取值非法，已保持旧配置继续服务",
  "data": null
}
```

验证结果：

- 服务未崩溃；
- 业务接口继续可用；
- 前端继续沿用旧配置行为。

结论：失败回退机制成立。

### 4.4 进程连续性

本方案为同一服务进程内执行配置切换，不依赖重启或新实例替换。  
即：满足考核“不停机更新”的核心要求。

### 4.5 Docker 场景验证

验证步骤：

1. 使用 `deploy/prod/docker-compose.yml` 启动服务；
2. 修改宿主机文件 `deploy/prod/runtime-config.yml` 并保存；
3. CI/CD 仅同步配置文件并调用 `POST /post/runtime/reload-config`；
4. 不重启后端容器，直接访问 `GET /post/runtime/config` 或业务接口。

验证结果：

- 配置变化可在容器运行中自动生效；
- 满足 Docker 场景下不停机配置热重载要求。

线上验证证据（节选）：

```text

...修改配置并触发 CI/CD 后再次查看...

StartedAt=2026-04-27T09:37:44.814540551Z  Status=running  RestartCount=0
```

结论：配置更新后后端容器未重启，满足不停机更新要求。

## 7. 逻辑热替换前置能力建设

为后续实现 Level 2（业务逻辑热重载），本项目已完成插件化基础抽象与运行时插件切换能力，核心目标是：

- 将“可变化的业务规则”从 `PostServerImpl` 中拆出；
- 通过统一接口与生命周期管理，为后续运行中替换逻辑做准备；
- 保持 Controller 与主业务流程稳定，减少替换逻辑时的改动面。

### 7.1 新增结构

新增规则插件相关模块：

- `RulePlugin<I, O>`：统一插件接口（`id / init / execute / dispose`）
- `PluginContext`：主系统提供的受控依赖边界
- `PageSizeRuleInput` / `PageSizeRuleOutput`：分页规则输入输出对象
- `DefaultPageSizeRulePlugin`：默认分页规则实现
- `RuntimeOnlyPageSizeRulePlugin`：运行时优先分页规则实现
- `PageSizeRuleEngineService`：规则引擎服务，负责委托插件执行

### 7.2 业务接入结果

- `PostServerImpl` 已由“直接 if/else 判定分页规则”改为“调用规则引擎”；
- Controller 无需改动；
- 日志新增规则原因输出（`reason`），便于确认规则命中路径。

### 7.3 两套分页规则的区别与切换方式

当前已实现两套分页规则插件，便于审核员理解“只换实现，不改 Controller，业务行为也会改变”：

| 插件 ID | 类名 | 规则含义 |
| --- | --- | --- |
| `default-page-size-rule` | `DefaultPageSizeRulePlugin` | 默认规则：优先尊重前端请求的 `pageSize`；若请求值非法，则回退到运行时配置；当 `strictModeEnabled=true` 时，强制使用运行时配置 |
| `runtime-only-page-size-rule` | `RuntimeOnlyPageSizeRulePlugin` | 运行时优先规则：忽略前端请求的 `pageSize`，始终使用 `runtime-config.yml` 中的 `postPageSize` |

切换方式有两种：

1. 修改 `runtime-config.yml` 中的 `pageSizeRulePluginId` 后触发配置热重载；
2. 调用演示接口手动切换分页规则插件。

示例：

```yaml
postPageSize: 5
strictModeEnabled: false
pageSizeRulePluginId: runtime-only-page-size-rule
```

此时即使前端请求 `pageSize=12`，分页规则仍会强制使用运行时配置中的 `5`。

### 7.4 当前定位与能力边界

当前已实现 **Level 2 前置能力建设**，包括“统一插件接口 + 两套规则实现 + 运行时切换当前插件”。

当前尚未实现“外部类动态加载 + 运行时替换外部插件文件”的完整 Level 2。

后续计划：

1. 引入类加载与热替换流程；
2. 完善旧插件资源释放与失败回退策略；
3. 将当前“切换已有实现”升级为“动态加载并切换新实现”。

### 7.5 当前已具备的逻辑切换能力

在现有插件化结构基础上，已完成“运行时切换当前插件”的能力，具体包括：

- 新增第二个插件实现 `RuntimeOnlyPageSizeRulePlugin`；
- 支持通过 `runtime-config.yml` 中的 `pageSizeRulePluginId` 动态选择当前规则插件；
- 提供手动切换接口与当前插件状态查询接口；
- 在规则引擎中补充“最近切换时间”“切换来源”等可观测信息；
- 将切换顺序调整为“先初始化新插件，再替换当前引用，最后释放旧插件”。

基于上述能力，当前已可验证：

1. Controller 无需改动；
2. 同一请求在不同插件实现下返回不同业务结果；
3. 服务运行中可切换逻辑实现，而无需重启主进程。

### 7.6 外部插件 jar 动态加载与切换（Level 2 基础能力演示）

在现有运行时插件切换能力基础上，已补充“手动加载外部插件 jar 并切换”的基础能力，具体包括：

- 新增 `ExternalPageSizePluginLoader`，负责从外部 jar 通过 `URLClassLoader` 动态加载插件类；
- 新增 `ExternalPageSizePluginLoadResult`，封装外部插件实例、类加载器、jar 路径与主类名；
- 规则引擎新增切换到外部插件的方法，支持在服务运行中将当前插件替换为 jar 中的新实现；
- 切换过程采用“先初始化新插件，再替换当前引用，最后释放旧插件并关闭旧外部类加载器”的顺序；
- 新增演示接口 `POST /post/runtime/load-external-page-size-plugin`，用于手动触发外部插件加载。

当前这部分能力属于 **Level 2 的基础版实现**：

- 已支持“运行中加载外部新逻辑并切换”；
- 尚未实现“自动监听外部插件 jar 文件变化并自动热切换”。

关键行为说明（避免验证时误判）：

- **外部插件接管后保持生效**：外部插件一旦通过接口加载并切换成功，后续业务请求会继续使用当前外部插件，不会被 `runtime-config.yml` 的 `pageSizeRulePluginId` 在每次请求时自动切回内置插件。
- **如何切回内置插件**：如需恢复配置驱动的内置插件体系，可调用 `POST /post/runtime/switch-page-size-rule` 手动切回 `default-page-size-rule` 或 `runtime-only-page-size-rule`。

### 7.7 外部插件演示模块

为方便本地演示，后端父工程下新增了 `blog-plugin-demo` 模块，用于单独产出一个外部插件 jar。

该模块特点如下：

- 与 `blog-server` 同仓库，但独立打包；
- 外部插件编译期仅引用宿主系统暴露的插件接口与 DTO（由宿主模块产物提供类路径）；
- 宿主模块 `blog-server` 会额外产出一个 `-plain.jar`（普通 jar），供外部插件模块编译期引用；
- 打包产物不会重新包含宿主接口定义，避免类加载类型不一致问题；
- 当前内置了一个演示插件：`cn.ayeez.blogplugindemo.paging.DoublePageSizeRulePlugin`。

该演示插件的行为很简单：

- 读取当前 `runtime-config.yml` 中的 `postPageSize`；
- 将最终生效分页大小固定计算为 `postPageSize * 2`；
- 返回明确的规则原因，便于观察外部插件是否已经接管。

### 7.8 外部插件本地演示步骤

1. 在 `AyeezBlog-Backend` 目录先构建宿主模块（必须带 `-am`，同时构建依赖模块）：
   `mvn -pl blog-server -am package`
   - 该命令会在 `blog-server/target/` 下生成 `blog-server-0.0.1-SNAPSHOT-plain.jar`
2. 再构建外部插件 jar：
   `mvn -pl blog-plugin-demo clean package`
   - 生成文件：`AyeezBlog-Backend/blog-plugin-demo/target/blog-plugin-demo-0.0.1-SNAPSHOT.jar`
3. 启动 `blog-server` 后，调用外部插件加载接口：
   `POST /post/runtime/load-external-page-size-plugin`
4. 传入两个参数（示例）：
   - `jarPath=D:/Develop/project/AyeezBlog/AyeezBlog-Backend/blog-plugin-demo/target/blog-plugin-demo-0.0.1-SNAPSHOT.jar`
   - `className=cn.ayeez.blogplugindemo.paging.DoublePageSizeRulePlugin`
5. 再调用：
   `GET /post/runtime/page-size-rule`
   可看到当前插件来源变为 `external`
6. 再请求业务分页接口，可观察到最终分页大小变为运行时配置的 2 倍（演示插件规则）。

### 7.9 外部插件自动热加载（插件目录监听）

在“外部插件 jar 动态加载与切换”的基础上，补充了**自动化触发**能力：当插件目录下的 `.jar` 发生变更时，后端会自动加载最新 jar 并切换当前插件，实现无需手动调用加载接口的逻辑热更新演示。

实现要点：

- 通过环境变量 `PAGE_SIZE_PLUGIN_DIR` 指定需要监听的插件目录；
- 后端启动后使用 `WatchService` 监听该目录的文件变更事件（创建/修改/删除）；
- 对保存/上传产生的高频事件做防抖处理；
- 对“半写入 jar”做稳定性检查（短时间内文件大小不再变化才尝试加载）；
- 自动选择目录内“最近一次修改时间最新”的 `.jar` 作为候选；
- 加载失败时保持当前插件继续服务（不影响业务可用性）；
- 切换成功后可通过接口查询当前来源与切换历史。

#### 7.9.1 插件元信息（plugin.properties）

为避免自动加载时还需要手动传入主类名，外部插件 jar 约定必须包含 `plugin.properties`：

- `plugin.id`：插件 ID（用于可读性与定位）
- `plugin.class`：插件主类全限定名（自动加载所需）
- `plugin.version`：插件版本（可选，建议提供）

示例：

```properties
plugin.id=double-page-size-rule
plugin.class=cn.ayeez.blogplugindemo.paging.DoublePageSizeRulePlugin
plugin.version=1.0.0
```

#### 7.9.2 本地验证步骤（自动热加载）

1. 准备一个插件目录（示例）：
   `D:/Develop/project/AyeezBlog/plugins/page-size`
2. 以环境变量方式启动 `blog-server`（示例）：
   - `PAGE_SIZE_PLUGIN_DIR=D:/Develop/project/AyeezBlog/plugins/page-size`
3. 将外部插件 jar 复制到该目录下：
   - 推荐先上传/复制为临时文件（如 `xxx.jar.tmp`），完成后再重命名为 `xxx.jar`，以减少“半写入”风险；
4. 等待防抖窗口结束后，调用：
   - `GET /post/runtime/page-size-rule`
   观察 `currentPluginOrigin` 变为 `external`；
5. 调用：
   - `GET /post/runtime/page-size-rule-history?limit=20`
   可看到最近一次切换来源为 `auto-watch` 的记录；
6. 再请求业务分页接口，观察规则结果已由外部插件接管。

#### 7.9.3 回退与恢复策略

如需从外部接管模式回退到“配置指定的内置插件”，可调用：

- `POST /post/runtime/revert-page-size-rule-to-configured`

该接口会读取当前 `runtime-config.yml` 的 `pageSizeRulePluginId` 并切回对应内置插件，恢复“配置驱动切换”的行为。
