## 2. 实现范围与核心设计

### 2.1 实现范围

本次交付以 **Level 1：配置文件热重载** 为主，同时补充了 **Level 2 的基础能力演示**（外部插件 jar 动态加载并切换当前规则实现），用于展示“逻辑热替换”的关键链路。

### 2.2 核心设计

为保证运行期间配置切换的安全性与可观测性，新增以下核心模块（我放在了`AyeezBlog-Backend/blog-server/src/main/java/cn/ayeez/blogserver/runtime/plugin`）：

- `RuntimeConfig`：运行时配置快照对象；
- `RuntimeConfigLoader`：负责配置文件读取与校验；
- `RuntimeConfigManager`：使用 `AtomicReference<RuntimeConfig>` 保存当前生效配置，支持原子切换；
- `RuntimeConfigWatchService`：基于 `WatchService` 监听配置文件变更并自动触发重载；
- `RuntimeConfigDemoController`：提供重载触发与验证接口。

### 2.3 配置切换策略

配置切换采用“先加载并校验、再原子替换”的策略

实现原理如下：

1. **触发阶段（自动）**
  - 自动触发：`RuntimeConfigWatchService` 监听到 `runtime-config.yml` 保存事件后触发重载；
  - 监听事件最终收敛到统一重载链路（`RuntimeConfigManager.reload()`）。
2. **加载阶段（不影响当前服务）**
  - `RuntimeConfigLoader` 从目标路径读取 YAML 并反序列化为新的 `RuntimeConfig` 候选对象；
  - 此时只是“候选配置”，尚未替换当前在线配置，对外请求仍读取旧快照。
3. **校验阶段（失败即终止）**
  - 执行字段完整性与业务约束校验（例如 `postPageSize` 取值范围、插件 ID 合法性）；
  - 任何校验失败都直接返回失败，不进入替换阶段。
4. **生效阶段（原子替换）**
  - 校验通过后，`RuntimeConfigManager` 通过 `AtomicReference<RuntimeConfig>` 一次性替换当前配置引用；
  - 原子替换保证并发请求下不会出现“半更新状态”：请求要么读到旧配置，要么读到新配置。
5. **请求可见性与回退语义**
  - 替换完成后，仅影响后续请求；已在执行中的请求继续使用其读取时拿到的配置快照；
  - 当加载或校验失败时，`AtomicReference` 不发生写入，系统继续使用上一版稳定配置，形成天然失败回退。

该策略在实现上同时满足了：不停机、并发安全、失败不扩散、行为可预测。

- 服务未崩溃；

## 7. 业务逻辑热重载实现原理

本项目的业务逻辑热重载实现方式是：把“会变化的业务规则”抽象为插件，由规则引擎在运行时托管当前插件实例，从而实现“主流程不改、规则可切换”。

核心执行链路如下：

1. 请求进入业务层后，`PostServerImpl` 不再直接写死分页规则，而是委托 `PageSizeRuleEngineService` 计算最终分页参数；
2. 规则引擎持有当前生效插件引用（内置插件或外部插件），并将请求参数封装为 `PageSizeRuleInput` 交给插件执行；
3. 插件返回 `PageSizeRuleOutput`（包含生效分页值与命中原因），业务层据此继续查询，Controller 无需感知插件来源；
4. 当发生热更新（目录监听自动加载）时，引擎按“先 `init` 新插件 -> 再切换当前引用 -> 最后 `dispose` 旧插件并关闭旧 `ClassLoader`”的顺序完成替换；
5. 若新插件加载或切换失败，则保持旧插件继续服务，避免业务中断或切到不可用状态；
6. 切换后的效果会直接体现在后续请求上，并可通过当前插件状态与切换历史接口观察。

### 7.1 新增结构

新增规则插件相关模块：

- `RulePlugin<I, O>`：统一插件接口（`id / init / execute / dispose`）
- `PluginContext`：主系统提供的受控依赖边界
- `PageSizeRuleInput` / `PageSizeRuleOutput`：分页规则输入输出对象
- `DefaultPageSizeRulePlugin`：默认分页规则实现
- `RuntimeOnlyPageSizeRulePlugin`：运行时优先分页规则实现
- `PageSizeRuleEngineService`：规则引擎服务，负责委托插件执行

### 7.2 当前能力

已实现外置插件链路：外部插件 jar 自动加载、目录监听自动热加载、失败保持当前插件继续服务。

### 7.3 外部插件 jar 自动加载与切换（Level 2 基础能力演示）

在现有运行时插件切换能力基础上，已补充“监听目录自动加载外部插件 jar 并切换”的基础能力，具体包括：

- 新增 `ExternalPageSizePluginLoader`，负责从外部 jar 通过 `URLClassLoader` 动态加载插件类；
- 新增 `ExternalPageSizePluginLoadResult`，封装外部插件实例、类加载器、jar 路径与主类名；
- 规则引擎新增切换到外部插件的方法，支持在服务运行中将当前插件替换为 jar 中的新实现；
- 切换过程采用“先初始化新插件，再替换当前引用，最后释放旧插件并关闭旧外部类加载器”的顺序；

当前这部分能力属于 **Level 2 的基础版实现（自动监听路径）**：

- 已支持“运行中加载外部新逻辑并切换”；
- 已支持“自动监听外部插件 jar 文件变化并自动热切换”（见 `7.5`）；
- 当前已实现基础副作用回收与资源释放，但“插件副作用彻底回收后的严格可逆卸载”仍属于后续增强项。

关键行为说明（避免验证时误判）：

- **外部插件接管后保持生效**：外部插件一旦被目录监听自动加载并切换成功，后续业务请求会继续使用当前外部插件，不会被 `runtime-config.yml` 的 `pageSizeRulePluginId` 在每次请求时自动切回内置插件。

### 7.4 外部插件演示模块

为方便本地演示，后端父工程下新增了 `blog-plugin-demo` 模块，用于单独产出一个外部插件 jar。

该模块特点如下：

- 与 `blog-server` 同仓库，但独立打包；
- 外部插件编译期仅引用宿主系统暴露的插件接口与 DTO（由宿主模块产物提供类路径）；
- 宿主模块 `blog-server` 会额外产出一个 `-plain.jar`（普通 jar），供外部插件模块编译期引用；
- 同时兼容 `compile` 与 `package` 两类构建流程：`blog-plugin-demo` 编译时会优先使用 `blog-server/target/classes`，并兼容 `-plain.jar`；
- 打包产物不会重新包含宿主接口定义，避免类加载类型不一致问题；
- 当前内置了一个演示插件：`cn.ayeez.blogplugindemo.paging.DoublePageSizeRulePlugin`。

该演示插件的行为很简单：

- 读取当前 `runtime-config.yml` 中的 `postPageSize`；
- 将最终生效分页大小固定计算为 `postPageSize * 2`；
- 返回明确的规则原因，便于观察外部插件是否已经接管。

### 7.5 外部插件自动热加载（插件目录监听）

在“外部插件 jar 动态加载与切换”的基础上，补充了**自动化触发**能力：当插件目录下的 `.jar` 发生变更时，后端会自动加载最新 jar 并切换当前插件，实现无需手动调用加载接口的逻辑热更新演示。

实现要点：

- 插件目录解析优先级：`PAGE_SIZE_PLUGIN_DIR`（环境变量） > `-Dpage.size.plugin.dir`（JVM 参数） > 默认目录 `plugins/page-size`；
- 后端启动后使用 `WatchService` 监听该目录的文件变更事件（创建/修改/删除）；
- 对保存/上传产生的高频事件做防抖处理；
- 对“半写入 jar”做稳定性检查（短时间内文件大小不再变化才尝试加载）；
- 自动选择目录内“最近一次修改时间最新”的 `.jar` 作为候选；
- 加载失败时保持当前插件继续服务（不影响业务可用性）；
- 切换成功后可通过接口查询当前来源与切换历史。

能力边界说明：

- 当前版本已实现“热加载切换与基础释放动作”，即在切换后执行旧插件 `dispose()` 与旧 `URLClassLoader.close()`；
- 这并不等价于“副作用彻底回收完成”：若插件内部创建线程/注册监听器/使用 `ThreadLocal` 或静态缓存，且插件未自行清理，仍可能残留引用或后台行为；
- 因此本项目当前可证明“热替换流程可跑通、失败可回退、业务不中断”，但不宣称“插件卸载后所有副作用 100% 可逆归零”。

#### 7.5.1 插件元信息（plugin.properties）

为避免自动加载时还需要手动传入主类名，外部插件 jar 约定必须包含 `plugin.properties`：

- `plugin.id`：插件 ID（用于可读性与定位）
- `plugin.class`：插件主类全限定名（自动加载所需）
- `plugin.version`：插件版本（可选，建议提供）

示例：

```properties
plugin.id=double-page-size-rule
plugin.class=cn.ayeez.blogplugindemo.paging.DoublePageSizeRulePlugin
plugin.version=1.0.0
```

#### 7.5.2 审核员验收效果步骤

为便于评审快速复现，建议按以下顺序执行：

1. **构建插件产物**
  - 目的：生成可用于目录监听热加载的外部插件 jar。
  - 操作：在 `AyeezBlog-Backend` 目录执行 `mvn compile -f pom.xml` 与 `mvn -pl blog-plugin-demo clean package`。
  - 通过标准：存在 `AyeezBlog-Backend/blog-plugin-demo/target/blog-plugin-demo-0.0.1-SNAPSHOT.jar`。
2. **准备演示数据**
  - 目的：保证分页效果可见，避免因样本过少导致观察不明显。
  - 操作：执行 `docs/sql/review-seed-posts.sql`（示例：`mysql -u root -p ayeezblog < docs/sql/review-seed-posts.sql`）。
  - 通过标准：数据库新增 40 篇审核演示文章（`review-post-`*）。
3. **启动后端并确认监听目录**
  - 目的：确保自动热加载线程已启动并监听目标目录。
  - 操作：启动 `blog-server`；默认监听 `AyeezBlog-Backend/plugins/page-size`。
  - 可选：如需改目录，设置 `PAGE_SIZE_PLUGIN_DIR` 或 `-Dpage.size.plugin.dir`。
4. **投放插件并触发自动加载**
  - 目的：触发 WatchService 自动检测并切换插件。
  - 操作：将 `blog-plugin-demo-0.0.1-SNAPSHOT.jar` 复制到监听目录。
  - 注意：建议先上传为 `xxx.jar.tmp`，复制完成后重命名为 `xxx.jar`，降低半写入误触发风险。
5. **验证插件是否已接管**
  - 目的：确认当前规则已切换到外部插件。
  - 操作：调用 `GET /post/runtime/page-size-rule`。
  - 通过标准：返回中 `currentPluginOrigin=external`。
6. **验证切换来源是否为自动监听**
  - 目的：确认本次切换由目录监听触发，而非人工介入。
  - 操作：调用 `GET /post/runtime/page-size-rule-history?limit=20`。
  - 通过标准：最新切换记录来源为 `auto-watch`。
7. **验证业务效果是否生效**
  - 目的：确认“插件已切换”不只是状态变化，而是确实影响业务请求。
  - 操作：调用业务分页接口并对比接管前后结果；也可直接在前端文章列表页观察分页条数变化。
  - 通过标准：分页规则体现外部插件逻辑（演示插件为 `postPageSize * 2`）。
8. **验证失败保护（负向用例）**
  - 目的：确认异常插件不会把在线服务切坏。
  - 操作：投放无效插件包（如缺少 `plugin.properties` 或主类不匹配）触发自动加载。
  - 通过标准：系统保持上一稳定插件继续服务，业务接口不中断。

为进一步满足“支持多次反复重载且无明显资源泄露”的评审要求，我采用了 **A/B 两轮对照试验**，并且两轮都按同一套流程执行了 **300 轮自动热加载**。  
其中：

- 当前默认行为：`plugin.sideeffect.cleanup=true`（默认执行清理）；
- **A 组**：在 JVM 显式传入 `-Dplugin.sideeffect.cleanup=false`，用于验证检测脚本是否能识别残留风险；
- **B 组**：不传该参数（或显式传 `-Dplugin.sideeffect.cleanup=true`），用于验证默认清理策略下资源与副作用可回收。

#### 7.5.3 评审测试脚本说明（A/B 对照，300 轮）

**测试方法**

- 方法一（功能稳定性）：`run-level2-auto-watch.ps1` 连续 300 轮投放插件 jar，验证自动监听切换与业务可用性；
- 方法二（健康汇总）：`check-level2-health.ps1` 汇总 `Origin/Source/Business` 指标；
- 方法三（资源与副作用回收）：`check-level2-leak-signals.ps1` 在“预热切换 -> 回退内置 -> 静默观察”后采样线程、内存与心跳副作用信号。

**A/B 统一测试流程（两组均执行）**

评审前说明（`scripts/review/output` 目录）：

- 该目录是脚本输出目录，默认可能保留我之前测试产生的历史数据；
- 评审员可先执行清理脚本清空目录，也可以不清理直接测试；
- 不清理也不影响本轮结论，因为后续脚本会用新生成的数据与报告直接覆盖同名文件。

可选清理命令：

- `powershell -ExecutionPolicy Bypass -File "scripts/review/cleanup-level2-review.ps1"`

1. 执行 300 轮自动热加载循环：
  - `powershell -ExecutionPolicy Bypass -File "scripts/review/run-level2-auto-watch.ps1" -Rounds 300`
2. 执行健康汇总检查：
  - `powershell -ExecutionPolicy Bypass -File "scripts/review/check-level2-health.ps1"`
3. 执行资源/副作用检测（8 次采样，每次间隔 3 秒）：
  - `powershell -ExecutionPolicy Bypass -File "scripts/review/check-level2-leak-signals.ps1" -Samples 8 -IntervalSeconds 3 -ExerciseRounds 30 -PostRevertQuietSeconds 10`
4. 备份本轮产物（便于 A/B 对照）：
  - A 组备份命令：
    - `Copy-Item "scripts/review/output/report.md" "scripts/review/output/report-A.md" -Force`
    - `Copy-Item "scripts/review/output/results.json" "scripts/review/output/results-A.json" -Force`
    - `Copy-Item "scripts/review/output/leak-signals-report.md" "scripts/review/output/leak-signals-report-A.md" -Force`
    - `Copy-Item "scripts/review/output/leak-signals.json" "scripts/review/output/leak-signals-A.json" -Force`
  - B 组备份命令：
    - `Copy-Item "scripts/review/output/report.md" "scripts/review/output/report-B.md" -Force`
    - `Copy-Item "scripts/review/output/results.json" "scripts/review/output/results-B.json" -Force`
    - `Copy-Item "scripts/review/output/leak-signals-report.md" "scripts/review/output/leak-signals-report-B.md" -Force`
    - `Copy-Item "scripts/review/output/leak-signals.json" "scripts/review/output/leak-signals-B.json" -Force`

**A 组结果（验证“脚本能抓到问题”）**

- 功能稳定性：`report-A.md` 显示 `300/300 PASS`，`Origin Mismatch=0`，`Source Mismatch=0`，`Business Failed=0`；
- 资源与副作用：`leak-signals-report-A.md` 显示 `MEDIUM_OR_HIGH`；
- 关键证据：
  - `回退后心跳线程数：987`
  - `回退后心跳日志增量：905115 bytes`
- 结论：A 组证明检测脚本有效，能够识别“回退后仍有副作用持续运行”的残留风险。

**B 组结果（验证“开启清理后确实释放资源”）**

- 功能稳定性：`report-B.md` 显示 `300/300 PASS`，`Origin Mismatch=0`，`Source Mismatch=0`，`Business Failed=0`；
- 资源与副作用：`leak-signals-report-B.md` 显示 `LOW`；
- 关键证据：
  - `心跳线程峰值：3`
  - `回退后心跳线程数：0`
  - `回退后心跳日志增量：0 bytes`
- 结论：B 组证明在开启清理后，副作用线程与写日志行为可在回退后归零，资源释放生效。

**对照试验总结合论**

- A/B 两组都完成了同样的 300 轮自动热加载，功能链路均稳定；
- A 组能稳定复现残留，说明检测脚本不是“只会报好结果”；
- B 组在同等压力下指标显著回落到可接受范围，证明资源释放与副作用回收逻辑已生效。

> 说明：`check-level2-leak-signals.ps1` 仍属于“风险信号检测”，不是法证级内存分析；如需更严格证明，可结合 `jcmd`、heap dump、MAT 做引用链排查。
