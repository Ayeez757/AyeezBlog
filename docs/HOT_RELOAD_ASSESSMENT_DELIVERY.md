# 第三轮后端考核交付文档（配置文件热重载）

## 1. 交付目标

本项目完成考核 `Level 1：配置文件热重载`。  
实现目标如下：

- 在服务不停机的前提下，动态加载新的运行时配置；
- 配置更新后可真实影响后续请求行为（前端可观察到分页条数变化）；
- 配置加载失败时保持上一版配置继续服务，不发生服务中断。

---

## 2. 实现范围与核心设计

### 2.1 实现范围

本次交付专注于 **配置文件热重载**，未实现业务逻辑模块热替换（Level 2）。

### 2.2 核心设计

为保证运行期间配置切换的安全性与可观测性，新增以下核心模块：

- `RuntimeConfig`：运行时配置快照对象；
- `RuntimeConfigLoader`：负责配置文件读取与校验；
- `RuntimeConfigManager`：使用 `AtomicReference<RuntimeConfig>` 保存当前生效配置，支持原子切换；
- `RuntimeConfigWatchService`：基于 `WatchService` 监听配置文件变更并自动触发重载；
- `RuntimeConfigDemoController`：提供重载触发与验证接口。

### 2.3 配置切换策略

配置切换采用“先加载、后替换”的安全流程：

1. 读取配置文件并反序列化；
2. 执行业务校验（例如 `postPageSize` 取值范围）；
3. 校验通过后原子替换当前配置；
4. 任一步失败则保持旧配置不变。

该策略确保系统在配置异常时仍可继续服务。

---

## 3. 配置文件与接口说明

### 3.1 配置文件

运行时配置文件：

- `AyeezBlog-Backend/blog-server/src/main/resources/runtime-config.yml`

当前示例字段：

- `postPageSize`：文章分页大小；
- `strictModeEnabled`：严格模式开关（开启后业务分页优先使用运行时配置值）。

### 3.2 演示接口

用于热重载验证的接口如下：

- `GET /post/runtime/config`：查看当前生效配置；
- `POST /post/runtime/reload-config`：手动触发配置重载；
- `GET /post/runtime/reload-config`：兼容浏览器调试；
- `GET /post/runtime/demo-cards`：演示配置变化对业务响应的影响。

自动触发机制：

- `WatchService` 监听 `runtime-config.yml` 文件变化；
- 保存配置文件后自动调用 `RuntimeConfigManager.reload()`；
- 含防抖策略，避免一次保存触发多次重复重载。

业务联动接口：

- `GET /api/post/list`：分页行为会受运行时配置影响（严格模式开启时可直接观察变化）。

## 4. 验证过程与结果

### 4.1 手动触发重载验证

验证步骤：

1. 启动后端服务；
2. 将 `runtime-config.yml` 中 `postPageSize` 改为合法值（如 `3`）；
3. 调用 `POST /post/runtime/reload-config`；
4. 再次访问 `GET /api/post/list` 或前端首页文章列表。

验证结果：

- 接口返回与前端展示均体现新分页大小；
- 后续请求行为已发生变化，证明重载生效。

### 4.2 自动触发重载验证（WatchService）

验证步骤：

1. 启动后端服务（确保监听线程已启动）；
2. 直接修改 `runtime-config.yml` 合法配置（如 `postPageSize`）并保存；
3. 不调用任何重载接口，直接访问 `GET /post/runtime/config` 或前端列表页面。

验证结果：

- 配置变更可自动生效；
- 后续请求行为同步变化；
- 自动触发能力通过测试。

### 4.3 失败回退验证

验证步骤：

1. 将 `runtime-config.yml` 设置为非法值（如 `postPageSize: 0`）；
2. 调用 `POST /post/runtime/reload-config`。

实际返回：

```json
{
  "code": 400,
  "message": "重载失败：配置文件格式或取值非法，已保持旧配置继续服务",
  "data": null
}
```

验证结果：

- 服务未崩溃；
- 业务接口继续可用；
- 前端继续沿用旧配置行为。

结论：失败回退机制成立。

### 4.4 进程连续性

本方案为同一服务进程内执行配置切换，不依赖重启或新实例替换。  
即：满足考核“不停机更新”的核心要求。

当前实现边界：
