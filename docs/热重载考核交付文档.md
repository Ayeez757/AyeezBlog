## 1. 交付目标

本项目完成考核 `Level 1：配置文件热重载`。  
实现目标如下：

- 在服务不停机的前提下，动态加载新的运行时配置；
- 配置更新后可真实影响后续请求行为（前端可观察到分页条数变化）；
- 配置加载失败时保持上一版配置继续服务，不发生服务中断。

> 评审说明：  
> 验收以「热重载行为可复现」为准：**优先**使用 `deploy/review` Docker 栈；代码分支为 `hotReload-v2`（[https://github.com/Ayeez757/AyeezBlog/tree/hotReload-v2](https://github.com/Ayeez757/AyeezBlog/tree/hotReload-v2)），从克隆到 **HTTP 自检通过**见第 4 节 **4.0.1**「一～五」。**栈内 Level2 开箱与自动化评审脚本**见 **7.5.0、7.5.3**。亦可使用本地 MySQL + 后端（**4.0.2**）。功能验证仍以 **4.1～4.2**（及 **7.5** 相关小节）为准。

## 2. 实现范围与核心设计

### 2.1 实现范围

本次交付实现了level1和level2的功能演示，（外部插件 jar 动态加载并切换当前规则实现），用于展示“逻辑热替换”的关键链路。

level2的资源释放、副作用回收完成了一部分，单一插件（不对其他插件造成副作用）反复加载卸载的产生的资源能够成功释放，但是无法做到多个互相影响的插件副作用逆序回收。

### 2.2 核心设计

为保证运行期间配置切换的安全性与可观测性，新增以下核心模块（我放在了`AyeezBlog-Backend/blog-server/src/main/java/cn/ayeez/blogserver/runtime/plugin`）：

- `RuntimeConfig`：运行时配置快照对象；
- `RuntimeConfigLoader`：负责配置文件读取与校验；
- `RuntimeConfigManager`：使用 `AtomicReference<RuntimeConfig>` 保存当前生效配置，支持原子切换；
- `RuntimeConfigWatchService`：基于 `WatchService` 监听配置文件变更并自动触发重载；
- `RuntimeConfigDemoController`：提供重载触发与验证接口。

### 2.3 配置切换策略

配置切换采用“先加载并校验、再原子替换”的策略

实现原理如下：

1. **触发阶段（自动）**
  - 自动触发：`RuntimeConfigWatchService` 监听到 `runtime-config.yml` 保存事件后触发重载；
  - 监听事件最终收敛到统一重载链路（`RuntimeConfigManager.reload()`）。
2. **加载阶段（不影响当前服务）**
  - `RuntimeConfigLoader` 从目标路径读取 YAML 并反序列化为新的 `RuntimeConfig` 候选对象；
  - 此时只是“候选配置”，尚未替换当前在线配置，对外请求仍读取旧快照。
3. **校验阶段（失败即终止）**
  - 执行字段完整性与业务约束校验（例如 `postPageSize` 取值范围、插件 ID 合法性）；
  - 任何校验失败都直接返回失败，不进入替换阶段。
4. **生效阶段（原子替换）**
  - 校验通过后，`RuntimeConfigManager` 通过 `AtomicReference<RuntimeConfig>` 一次性替换当前配置引用；
  - 原子替换保证并发请求下不会出现“半更新状态”：请求要么读到旧配置，要么读到新配置。
5. **请求可见性与回退语义**
  - 替换完成后，仅影响后续请求；已在执行中的请求继续使用其读取时拿到的配置快照；
  - 当加载或校验失败时，`AtomicReference` 不发生写入，系统继续使用上一版稳定配置，形成天然失败回退。

该策略在实现上同时满足了：不停机、并发安全、失败不扩散、行为可预测。

**七、常见问题（分点 + 可复制命令）**

下列 `docker compose` 片段默认在 **仓库根** 下先执行 `cd deploy/review`（含义见本节上文 **「Compose 工作目录」**）；从空目录克隆的例外见条目「挂载 … 失败」。

1. `**exec /app/docker-entrypoint.sh: no such file or directory`**
  - 多为 **shell 脚本 CRLF 行尾**（Windows 检出）。请拉取含 Dockerfile 中 `sed` 去 `\r` 的提交；本地也可将 `AyeezBlog-Backend/docker/review-entrypoint.sh` 转为 LF 后重建。

```bash

docker compose build --no-cache backend
docker compose up -d
```

2. `**backend` 构建很慢或超时**
  - 先检查网络与 Maven Central 可达性，再在评审 compose 目录重试全量构建：

```bash
cd deploy/review
docker compose up --build
```

3. **端口已被占用**
  - 编辑 `deploy/review/.env`（仓库根下相对路径），修改 `REVIEW_BACKEND_PORT`、`REVIEW_NGINX_PORT`、`REVIEW_MYSQL_PORT` 后强制重建：

```bash

docker compose up -d --build --force-recreate
```

  - **典型报错**：`ports are not available ... listen tcp 0.0.0.0:33060: bind: Only one usage of each socket address ...`（或其它映射端口同理），说明宿主机该端口已被占用。
  - **`taskkill /PID … /F` 提示「拒绝访问」**：占用进程可能是系统服务、其它用户会话或受保护进程（本机 **33060** 常见于 **MySQL X Protocol** 或残留 Docker 代理）。**优先**改 `.env` 里 `REVIEW_MYSQL_PORT` 换空闲端口再 `docker compose up`；若必须结束进程，用**管理员**终端执行 `taskkill`，或在「服务」中停用对应服务（如本地 MySQL）、先 `docker compose down` / 退出占用该端口的容器后再试。

4. **挂载 `AyeezBlog建表.sql` 失败**
  - 必须在**完整仓库**内执行 compose；若从空目录开始，先克隆再进入 `deploy/review`：

```bash
git clone --branch hotReload-v2 --single-branch https://github.com/Ayeez757/AyeezBlog.git
cd AyeezBlog/deploy/review
docker compose up --build
```

5. **改动了 SQL，想重新导入**
  - 删除数据卷后重新拉起（会清空评审库数据）：

```bash
cd deploy/review
docker compose down -v
docker compose up -d --build
```

6. **只想重启应用、不改库**

```bash
cd deploy/review
docker compose restart backend
```

## 7. 业务逻辑热重载实现原理

本项目的业务逻辑热重载实现方式是：把“会变化的业务规则”抽象为插件，由规则引擎在运行时托管当前插件实例，从而实现“主流程不改、规则可切换”。

核心执行链路如下：

1. 请求进入业务层后，`PostServerImpl` 不再直接写死分页规则，而是委托 `PageSizeRuleEngineService` 计算最终分页参数；
2. 规则引擎持有当前生效插件引用（内置插件或外部插件），并将请求参数封装为 `PageSizeRuleInput` 交给插件执行；
3. 插件返回 `PageSizeRuleOutput`（包含生效分页值与命中原因），业务层据此继续查询，Controller 无需感知插件来源；
4. 当发生热更新（目录监听自动加载）时，引擎按“先 `init` 新插件（插件登记资源）-> 再切换当前引用 -> 最后 `dispose` 旧插件并触发平台统一回收 + 关闭旧 `ClassLoader`”的顺序完成替换；
5. 若新插件加载或切换失败，则保持旧插件继续服务，避免业务中断或切到不可用状态；
6. 切换后的效果会直接体现在后续请求上，并可通过当前插件状态与切换历史接口观察。

> **第三方 SDK 说明**（外置 jar 开发）：除下文各小节外，另有一份仅面向接口与构建的摘要文档 [分页规则插件 · 第三方 SDK 说明](./分页规则插件_第三方SDK说明.md)，便于与交付步骤拆阅。

### 7.1 新增结构

新增规则插件相关模块：

- `RulePlugin<I, O>`：统一插件接口（`id / init / execute / dispose`）
- `PluginContext`：主系统提供的受控依赖边界
- `PageSizeRuleInput` / `PageSizeRuleOutput`：分页规则输入输出对象
- `DefaultPageSizeRulePlugin`：默认分页规则实现
- `RuntimeOnlyPageSizeRulePlugin`：运行时优先分页规则实现
- `PageSizeRuleEngineService`：规则引擎服务，负责委托插件执行

### 7.2 当前能力

已实现外置插件链路：外部插件 jar 自动加载、目录监听自动热加载、失败保持当前插件继续服务。

### 7.3 外部插件 jar 自动加载与切换（Level 2 基础能力演示）

在现有运行时插件切换能力基础上，已补充“监听目录自动加载外部插件 jar 并切换”的基础能力，具体包括：

- 新增 `ExternalPageSizePluginLoader`，负责从外部 jar 通过 `URLClassLoader` 动态加载插件类；
- 新增 `ExternalPageSizePluginLoadResult`，封装外部插件实例、类加载器、jar 路径与主类名；
- 规则引擎新增切换到外部插件的方法，支持在服务运行中将当前插件替换为 jar 中的新实现；
- 切换过程采用“先初始化新插件，再替换当前引用，最后释放旧插件并关闭旧外部类加载器”的顺序；

当前这部分能力属于 **Level 2 的基础版实现（自动监听路径）**：

- 已支持“运行中加载外部新逻辑并切换”；
- 已支持“自动监听外部插件 jar 文件变化并自动热切换”（见 `7.5`）；
- 当前已实现基础副作用回收与资源释放，但“插件副作用彻底回收后的严格可逆卸载”仍属于后续增强项。

关键行为说明（避免验证时误判）：

- **外部插件接管后保持生效**：外部插件一旦被目录监听自动加载并切换成功，后续业务请求会继续使用当前外部插件，不会被 `runtime-config.yml` 的 `pageSizeRulePluginId` 在每次请求时自动切回内置插件。

### 7.4 外部插件演示模块

`RulePlugin` / `PluginContext` / 分页 DTO 的契约与第三方编译依赖，见 [分页规则插件 · 第三方 SDK 说明](./分页规则插件_第三方SDK说明.md)。本节说明本仓库内演示模块与构建产物。

为方便本地演示，后端父工程下新增了 `blog-plugin-demo` 模块，用于单独产出一个外部插件 jar。

该模块特点如下：

- 与 `blog-server` 同仓库，但独立打包；
- 外部插件编译期仅引用宿主系统暴露的插件接口与 DTO（由宿主模块产物提供类路径）；
- 宿主模块 `blog-server` 会额外产出一个 `-plain.jar`（普通 jar），供外部插件模块编译期引用；
- 同时兼容 `compile` 与 `package` 两类构建流程：`blog-plugin-demo` 编译时会优先使用 `blog-server/target/classes`，并兼容 `-plain.jar`；
- 打包产物不会重新包含宿主接口定义，避免类加载类型不一致问题；
- 默认可加载演示插件：`cn.ayeez.blogplugindemo.paging.StatefulSideEffectPageSizeRulePlugin`（`plugin.properties` 默认指向该类，含心跳副作用，供 **7.5.3** A/B 与泄露脚本对照）。
- 另有简单实现 `cn.ayeez.blogplugindemo.paging.DoublePageSizeRulePlugin`：将分页固定为 `postPageSize * 2`、无副作用；默认一次 `mvn package` 同时产出 **`blog-plugin-demo-0.0.1-SNAPSHOT-double.jar`**（其 `plugin.properties` 仅在 **`blog-plugin-demo/pom.xml`** 的打包步骤中生成，源码树只保留一份 `plugin.properties`）。

**StatefulSideEffect** 行为概要：

- 读取 `postPageSize`，生效值约为 `postPageSize * 2` 加少量有状态增量；
- 心跳线程写 `plugins/page-size/side-effect-heartbeat.log`，配合 `pluginCleanupEnabled` 做回收对照；
- 返回规则原因字符串，便于确认外部插件已接管。

**7.5 外部插件自动热加载（插件目录监听）**

小节索引：**7.5.0**（评审 Docker ：Level1/Level2 开箱、路径、压测入口）→ **7.5.1**（`plugin.properties`）→ **7.5.2**（验收步骤）→ **7.5.3**（**A/B 两轮 300 轮**：逐步说明与命令、泄露检测备选 + **结果判读**）。

在“外部插件 jar 动态加载与切换”的基础上，补充了**自动化触发**能力：当插件目录下的 `.jar` 发生变更时，后端会自动加载最新 jar 并切换当前插件，实现无需手动调用加载接口的逻辑热更新演示。

实现要点：

- 插件目录解析优先级：`PAGE_SIZE_PLUGIN_DIR`（环境变量） > `-Dpage.size.plugin.dir`（JVM 参数） > 默认目录 `plugins/page-size`；
- 后端启动后使用 `WatchService` 监听该目录的文件变更事件（创建/修改/删除）；
- 对保存/上传产生的高频事件做防抖处理；
- 对“半写入 jar”做稳定性检查（短时间内文件大小不再变化才尝试加载）；
- 自动选择目录内“最近一次修改时间最新”的 `.jar` 作为候选；
- 加载失败时保持当前插件继续服务（不影响业务可用性）；
- 切换成功后可通过接口查询当前来源与切换历史。
- 插件资源回收采用“插件登记 + 平台统一回收”机制：插件在 `init` 阶段通过 `PluginContext.registerCleanupAction(...)` 登记自身创建的可回收资源（如线程池、定时任务等）；
- 规则引擎在插件下线阶段按“先 `dispose` 旧插件，再执行平台登记的清理动作，最后关闭旧 `ClassLoader`”顺序回收资源，避免切换窗口中的资源悬挂；
- 是否执行平台回收由运行时配置 `runtime-config.yml` 中 `pluginCleanupEnabled` 控制（`true` 执行回收，`false` 跳过回收用于 A 组残留对照）；
- 外部插件初始化失败时，引擎会对“新插件半初始化资源 + 新 `ClassLoader`”执行即时清理，避免失败路径残留。

能力边界说明：

- 当前版本已实现“插件登记 + 平台回收”的基础治理：切换后会调用旧插件 `dispose()`，并执行平台登记的回收动作与旧 `URLClassLoader.close()`；
- 这并不等价于“所有类型副作用 100% 覆盖”：若插件未按规范登记某些资源（如自建线程、监听器、ThreadLocal、静态缓存），仍可能存在残留风险；
- 因此本项目当前可证明“热替换流程可跑通、失败可回退、业务不中断”，但不宣称“插件卸载后所有副作用 100% 可逆归零”。

### 7.5.1 插件元信息（plugin.properties）

键语义及 jar 根路径要求与第三方摘要一致，见 [分页规则插件 · 第三方 SDK 说明](./分页规则插件_第三方SDK说明.md) 第 5 节。

为避免自动加载时还需要手动传入主类名，外部插件 jar 约定必须包含 `plugin.properties`：

- `plugin.id`：插件 ID（用于可读性与定位）
- `plugin.class`：插件主类全限定名（自动加载所需）
- `plugin.version`：插件版本（可选，建议提供）

示例：

```properties
plugin.id=stateful-side-effect-page-size-rule
plugin.class=cn.ayeez.blogplugindemo.paging.StatefulSideEffectPageSizeRulePlugin
plugin.version=1.0.0-stateful
```

### 7.5.3 评审测试脚本说明（A/B 对照，300 轮）

在相同 **300 轮自动热加载** 压力下做 **A/B 两轮对照**：唯一变量为 `deploy/review/runtime-config.yml` 中的 `**pluginCleanupEnabled`**。默认 **Docker 评审栈**（Nginx **8888**）；栈部署见 **4.0.1**，插件路径与端口见 **7.5.0**。

#### A/B 试验目的


| 组别      | `pluginCleanupEnabled` | 目的                                                               |
| ------- | ---------------------- | ---------------------------------------------------------------- |
| **A 组** | `**false`**            | 关闭平台统一回收，使副作用可残留；验证 `check-level2-leak-signals` 能否报出较高风险（验证脚本有用） |
| **B 组** | `**true`**（与仓库默认一致）    | 开启回收；在同等 300 轮压力下验证泄露报告风险等级回落（「开启清理后有效」）                         |


仓库默认行为为 `**true`**；A 组为对照而临时改为 `**false**`。

#### 总执行顺序（必读）

1. **（可选）** 仅当你要**从零开始一整轮 A+B** 时，执行下文 **「可选：cleanup」**。**A 组尚未备份完毕时不要 cleanup**；**A 组与 B 组之间也不要 cleanup**，以免删掉正在使用的产出。
2. **完成 A 组**：按 **「A 组执行步骤」** 依次做完 A.1～A.7（含将报告与 JSON **备份为 `*-A.*`**）。
3. **切换到 B 组**：把 `runtime-config.yml` 中的 `pluginCleanupEnabled` 改回 `true`，按 **B.2** 重启 `backend`，再依次做完 B.3～B.7。**B.4 会覆盖**仓库内当前的 `report.md`、`results.json` 等，因此 **必须先完成 A.7**。
4. 打开 `scripts/review/output/` 下各轮备份的 `report-*.md`、`leak-signals-report-*.md`，按 **「结果判读」** 对照。

**耗时提示（便于排期）**：单机实测量级供参考——**一轮 300 轮**压测约 **13～15 分钟**（`WAIT_SECONDS` 等默认值下）；**两轮**约半小时量级；每次泄露检测（默认 8 采样、`http` 模式）约 **1～2 分钟**，`docker`/`host` 模式可能更长。**不含**首次镜像构建（构建本身才可能「数分钟～十余分钟」）。

#### 结果判读（看趋势，不抠固定数字）

泄露脚本属于**短时窗口内的风险信号**汇总，具体数值会随 **JDK 版本、`jcmd` 输出格式、`--mode docker` 下 sidecar 采样路径、是否启用 GC.class_histogram 兜底、历史心跳日志是否清空** 等变化；**不要**用某一环境下的固定整数（如某次样例中的线程峰值、某次 `URLClassLoader` 读数）作为唯一通过标准。应以 **A/B 相对趋势** 与 **`riskLevel` 字段** 为主。

**A 组（`pluginCleanupEnabled: false`）——预期趋势**

- 功能稳定性：`report-A.md` 中 **300/300 PASS**（或你设定的轮数全部成功），`Origin Mismatch=0`，`Source Mismatch=0`，`Business Failed=0`；
- 资源与副作用：`leak-signals-report-A.md` 的 **`riskLevel` 倾向为 `MEDIUM_OR_HIGH`**（表示在短采样窗口内出现了若干条风险项，例如：回退后心跳相关线程或日志仍在增长、进程线程/私有内存/URLClassLoader 计数在窗口内明显抬升、jar 临时拷贝删除失败等中的**任意组合**）；
- 判读要点：关注 **「风险项」** 小节是否列出具体告警，以及 **采样表** 中各列是否随轮次呈不利方向的**趋势**（不同环境下 `jcmdThreads`、`urlClassLoaders` 可能为 `0`/`null`，以脚本说明与本节下文「模式差异」为准）。

**B 组（`pluginCleanupEnabled: true`）——预期趋势**

- 功能稳定性：与 A 组相同，压测报告应仍为全通过；
- 资源与副作用：在 **`docker` / `host`（`jcmd`）** 模式下，备份后的 `**leak-signals-report-B.md`**（或当前轮的 `**leak-signals-report.md**`）的 **`riskLevel` 倾向为 `LOW`**。若使用 **`http`** 模式，B 组 **`riskLevel` 仍可能为 `MEDIUM_OR_HIGH`**（窄口径下常见）；此时以 **B 相对 A** 是否减弱为准（回退后心跳线程数、日志增量、风险项条数等），**不要**强求与 `jcmd` 模式下的 **`LOW`** 字面一致。
- 与 A 组相比，上述指标应整体**不劣于 A 组**（常见情形是回退后心跳线程与日志增长类告警减弱或消失）。
- 判读要点：若 **`jcmd`** 模式下 B 组仍长期为 `MEDIUM_OR_HIGH`，优先按文末「说明」排查环境（未重启、插件目录不一致、历史 `side-effect-heartbeat.log` 未删等）。

**对照试验总结合论**

- A/B 在**相同压测轮数与相同插件目录**下，唯一变量为 `pluginCleanupEnabled`；
- **A 组**应能更频繁地触发「回收关闭后的残留信号」，证明检测脚本**不是**只会输出低风险；
- **B 组**在开启平台回收后，同类信号应整体**减弱或消失**，与「回收逻辑生效」的叙述一致。
- 若复测时出现 A/B **风险等级反转或与预期相反**，优先排查：是否遗漏重启后端、是否混用了插件目录、是否保留了上轮 `side-effect-heartbeat.log`、以及 **`--mode docker`** 下 `jcmd` 解析是否与 `host` 一致（部分 JDK 下 `URLClassLoader` 计数可能为 `null`，属环境差异，以趋势与其它风险项为准）。

> 说明：`check-level2-leak-signals` 仍属「风险信号检测」，不是法证级内存分析；`**--mode http`** 下内存列为 **JVM heap** 口径，与 **host / docker（`jcmd`）** 的进程侧指标不同，且不提供 `URLClassLoader` 计数；`**--mode docker`** 与 `**host`** 同为 `**jcmd**` 全量输出，差异主要在采样路径（容器 PID 命名空间 vs 本机进程）。在 **`http`** 下 A、B 两组都可能仍为 **`MEDIUM_OR_HIGH`**（风险项阈值未针对窄口径单独校准），**验收时请对照「结果判读」看 B 相对 A 是否减弱**（例如回退后心跳线程数、日志增量是否小于 A），而不要强求 B 组必定显示 **`LOW`**。如需更严格证明，可结合 **heap dump、MAT** 等做引用链排查。
